# Этап 10: микро-роадмап

Этот документ разбивает этап «Evals и observability» на небольшие проверяемые
итерации. Каждая итерация завершается отдельным коммитом.

Вернуться к общей карте: [ROADMAP.md](./ROADMAP.md).

## Граница этапа

Целевой процесс:

1. версионированный dataset описывает вход, начальное состояние и критерии;
2. runner поднимает изолированное состояние для каждого сценария;
3. fake LLM детерминированно выполняет обязательный CI-набор;
4. evaluator проверяет tools, аргументы, лимит шагов и итоговую БД;
5. отчёт считает task success, precision/recall, ошибки, шаги и usage;
6. любой провал содержит `run_id` и безопасную redacted trace;
7. live runner запускается только явно;
8. два отчёта сравниваются на одной версии dataset.

Не добавляем распределённый tracing backend, dashboards, LLM-as-a-judge,
статистическую значимость на малой выборке или автоматический production
monitoring. Сначала строим воспроизводимый локальный контур измерения.

## 10.1. Контракты и версионированный dataset

### Результат

Схема eval-сценария валидирует минимум 20 разнообразных примеров до запуска.

### Реализация

- Pydantic-контракты dataset и сценария.
- Input, initial state, expected/optional/forbidden tools.
- Инварианты аргументов, final-state assertions и max steps.
- Scripted responses только для обязательного fake режима.
- Версия dataset и версия prompt.

### Проверка

- Дубликаты ID и пересечения tool-групп отклоняются.
- Каждый сценарий содержит проверяемый final state.
- Dataset загружается одной командой без сети.

## 10.2. Детерминированный evaluator

### Результат

Evaluator отличает правильный tool path от запрещённого или неполного и не
принимает красивый ответ при неверном состоянии БД.

### Реализация

- Проверка expected/optional/forbidden calls без требования лишней строгости к
  последовательности.
- Проверка argument invariants.
- Проверка run status, library state и фрагментов ответа.
- Отдельная причина каждого провала.

### Проверка

- Unit-тесты precision/recall, forbidden calls и max steps.
- Неверный final state всегда делает scenario failed.

## 10.3. Изолированный fake runner и метрики

### Результат

Одна команда выполняет весь dataset на свежей SQLite для каждого сценария и
печатает агрегированный JSON-отчёт.

### Реализация

- Подготовка seed, библиотеки, заметок и preferences.
- Реальный AgentService и ToolRegistry с FakeLLMProvider.
- Метрики task success, tool precision/recall, invalid/forbidden calls,
  step count, latency и tokens при наличии.
- Regression test полного dataset.

### Проверка

- Обязательный runner не использует сеть или API key.
- Критические сценарии имеют ноль forbidden calls.
- Повторный запуск даёт одинаковые оценки.

## 10.4. Наблюдаемая трасса и redaction

### Результат

Run хранит provider, model и prompt version, а eval trace показывает полезную
структуру без секретов и содержимого sensitive fields.

### Реализация

- Миграция trace metadata.
- Usage на уровне шага и суммарно в отчёте.
- Безопасное представление tool name, redacted arguments/result, error,
  duration и final status.
- Рекурсивная redaction API keys, authorization, password, secret, token и
  явно sensitive полей заметок.

### Проверка

- Успешный и упавший run сохраняют trace.
- Секреты отсутствуют в сериализованном отчёте.

## 10.5. CLI, live opt-in и сравнение отчётов

### Результат

Fake eval запускается одной документированной командой; real-model eval требует
явного флага; два отчёта сравниваются только при одинаковом dataset.

### Реализация

- CLI с `fake` по умолчанию и явным `deepseek` режимом.
- Запись JSON-отчёта по запросу пользователя.
- Фиксация provider/model/prompt version.
- Команда сравнения двух отчётов и дельт метрик.

### Проверка

- Fake CLI работает без ключа.
- Live CLI без ключа завершается контролируемой ошибкой.
- Сравнение разных версий dataset отклоняется.

## 10.6. Сквозная приёмка и закрытие этапа

### Результат

Полный dataset, backend, PostgreSQL contract и frontend проходят; документация
объясняет не только команды, но и смысл измеряемых показателей.

### Реализация

- Acceptance-тест отчёта и связи failure → safe trace → run ID.
- Постоянный regression case для ошибки «правильный текст, неверная БД».
- Обновление README и ROADMAP.
- Итоговый отчёт с ограничениями и следующими экспериментами.

### Проверка

- Dataset содержит не меньше 20 сценариев.
- Любой failure диагностируется по безопасной трассе.
- Основной CI-набор не зависит от платного API.

## Отчёт о завершении этапа

Этап завершён 14 сентября 2026 шестью микроэтапами после отдельного
планирующего коммита.

**Что сделано.** Добавлены versioned dataset, строгие eval-контракты, чистый
evaluator, изолированный fake runner, агрегированные метрики, trace metadata,
usage, redaction, safe traces, CLI для fake/live режима и сравнение отчётов.

**Зачем.** Качество агента теперь определяется воспроизводимыми критериями, а не
впечатлением от одного ответа. Ошибку можно связать с конкретным run и понять,
сломалась модель, tool, аргумент или проверяемое состояние.

**На что обратить внимание.** Dataset мал и scripted baseline всегда
детерминирован. Он защищает механику и регрессии приложения, но не измеряет
статистическую устойчивость реальной LLM. Live-прогоны нужно повторять и
сравнивать отдельно, не ослабляя критерии под ответы модели.

**Как проверено.** Dataset проходит без сети, regression case намеренно падает
при красивом ответе и неверной БД, safe trace существует для success/failure,
секреты проходят redaction, миграции проверяются на SQLite и PostgreSQL.

**Что мы выучили.** Eval — это версия входных данных плюс неизменные критерии и
наблюдаемое состояние. Trace объясняет результат, но сама по себе не определяет
успех; метрика полезна только тогда, когда известно, что именно она считает.
