# Этап 7: микро-роадмап

Этот документ разбивает этап «React-интерфейс» на небольшие проверяемые
итерации. Мы проходим их строго по порядку. После каждой итерации приложение
остаётся рабочим, а все ранее реализованные backend-сценарии продолжают
проходить.

Вернуться к общей карте: [ROADMAP.md](./ROADMAP.md).

## Граница этапа

Целевой пользовательский процесс:

1. пользователь формулирует запрос в браузере;
2. frontend отправляет его в существующий agent API;
3. backend выполняет agent loop и возвращает сохранённый `AgentRun`;
4. интерфейс показывает ответ, статус и понятный ход запуска;
5. destructive-действие останавливается на `waiting_for_approval`;
6. пользователь явно выбирает approve или reject;
7. frontend отправляет только идентификаторы сохранённого решения;
8. после обновления страницы незавершённый run восстанавливается из backend;
9. пользователь видит итоговое состояние своей библиотеки.

На этом этапе мы не переносим agent loop в браузер, не добавляем frontend-
фреймворк агентов, авторизацию нескольких пользователей, WebSocket, сложный
роутинг, глобальный state manager, офлайн-режим и универсальную дизайн-систему.
Streaming допускается только после полностью рабочего синхронного процесса и
не входит в обязательную границу этапа.

## Принятые решения

- Backend остаётся источником истины для run, steps, pending action и
  библиотеки. React хранит только временное состояние интерфейса и ссылку на
  активный run для восстановления.
- Frontend не выбирает tools и не интерпретирует их arguments. Он отображает
  уже принятые backend решения и вызывает разрешённые HTTP endpoints.
- Approval-карточка показывает `summary`, сформированный backend. Approve и
  reject не отправляют arguments повторно.
- Первая версия использует обычный синхронный HTTP. Loading сообщает ожидание,
  но не притворяется streaming agent loop.
- Типы frontend повторяют публичные HTTP DTO, а не ORM-модели и не внутренние
  Python-классы.
- История одной browser session может жить локально, но долговечное состояние
  незавершённого процесса всегда перечитывается по run ID.
- Сначала доказывается поведение компонентов и API-клиента, затем добавляется
  E2E. Красивый экран без проверяемого пользовательского процесса не закрывает
  микроэтап.

## Рабочий договор для каждой итерации

Каждый микроэтап заканчивается отдельным коммитом и учебным отчётом:

1. **Что сделано:** изменённые контракты, поток данных и наблюдаемый результат.
2. **Зачем это нужно:** какую пользовательскую или архитектурную проблему
   устраняет изменение.
3. **Как это работает простыми словами:** путь от действия пользователя до
   видимого результата без пересказа кода построчно.
4. **На что обратить внимание:** инварианты, компромиссы и типичные ошибки.
5. **Как проверено:** названия тестов, команды, ручной smoke и фактический
   результат.
6. **Что мы выучили:** новые понятия и выводы, которые можно перенести в другой
   проект.
7. **Советы на будущее:** что станет важно позже, но не должно усложнять
   текущую итерацию.
8. **Самоконтроль:** ответы на вопросы своими словами до перехода дальше.

Если критерий готовности не выполнен или отчёт не написан, микроэтап не
считается завершённым. Сначала согласуется этот микро-роадмап, затем начинается
7.1. Уже созданные незакоммиченные frontend-файлы считаются черновиком, а не
доказательством завершения итерации.

## 7.1. Основа frontend и один завершённый запрос

### Результат итерации

Пользователь вводит сообщение в браузере, отправляет его и получает финальный
ответ завершённого agent run. Во время запроса виден loading, а недоступный API
завершает ожидание понятной ошибкой.

### Что реализуем

- Инициализируем `frontend/` на React, TypeScript и Vite.
- Настроим dev proxy с `/api` на локальный FastAPI.
- Опишем минимальные публичные DTO, необходимые для создания run.
- Реализуем пустое состояние, форму сообщения и локальную историю текущей
  browser session.
- Покажем loading только пока HTTP-запрос действительно выполняется.
- Покажем `final_answer` для `completed` и безопасное сообщение при сетевой или
  HTTP-ошибке.
- Добавим component-тест успешного запроса и негативный тест недоступного API.

### Зачем это нужно

Это самый маленький вертикальный срез между React и уже работающим agent API.
Он отдельно проверяет базовую границу браузер → HTTP → backend → ответ, не
смешивая её с trace, approval и восстановлением состояния.

### Как это должно работать простыми словами

Пользователь пишет просьбу и нажимает кнопку. React временно блокирует повторную
отправку и показывает, что запрос выполняется. Backend сам решает, какие tools
нужны, и возвращает готовый run. React берёт из него финальный ответ и добавляет
в диалог. Если сервер недоступен, интерфейс заканчивает loading и предлагает
повторить запрос вместо бесконечного ожидания.

### На что обратить внимание

- Пустая строка не должна уходить в API.
- Ошибка сети и контролируемая ошибка backend различаются технически, но обе
  должны быть понятны пользователю и не раскрывать stack trace.
- Кнопка повторной отправки блокируется только на время активного запроса.
- Frontend не пытается самостоятельно продолжать run или вызывать tool.
- DTO описывают только реально используемый публичный контракт.
- Trace и approval пока не входят в результат 7.1, даже если черновой код уже
  содержит их элементы.

### Проверка

- Component: введённый текст отправляется в `POST /api/agent/runs` один раз.
- Component: `completed` показывает `final_answer`.
- Негативный component: rejected fetch/HTTP error снимает loading и позволяет
  ввести следующий запрос.
- Build: TypeScript и production bundle собираются без ошибок.
- Ручной smoke: форма работает с клавиатуры на desktop и mobile.

### Критерий готовности

Один завершённый run проходит от формы до ответа в браузере, а недоступный API
не оставляет интерфейс в loading. Тесты доказывают оба пути, написан учебный
отчёт, создан отдельный коммит.

### Самоконтроль

**Почему frontend не должен вызывать `search_books` напрямую для сообщения
пользователя?**

Пользователь задаёт цель, а выбор последовательности tools является задачей
backend agent loop. Прямой вызов из React продублирует orchestration и создаст
второй источник правил.

**Чем server state отличается от локального текста в textarea?**

Run и его итог существуют независимо от конкретного React-компонента и могут
быть перечитаны с сервера. Текст ещё не отправленного сообщения нужен только
текущему интерфейсу и исчезновение этого значения не меняет backend.

**Почему обычный loading не означает streaming?**

Loading сообщает только, что один HTTP-запрос ещё не завершён. Streaming
передаёт промежуточные события или части ответа. Agent loop одинаково остаётся
на backend в обоих случаях.

### Совет на будущее

Не добавлять React Query, Zustand или роутер ради одного запроса. Эти
зависимости оправданы только после появления реальной повторяющейся задачи,
которую локальное состояние и маленький API client уже не решают.

### Отчёт о завершении 7.1

#### Что сделано

- Создан отдельный React + TypeScript + Vite frontend.
- Настроен dev proxy: браузер обращается к `/api`, а Vite во время разработки
  пересылает запросы локальному FastAPI на `127.0.0.1:8000`.
- Добавлен минимальный API client только для `POST /api/agent/runs` и DTO с
  полями, которые действительно нужны этому экрану.
- Реализованы пустое состояние, примеры запросов, форма, локальная история,
  loading, финальный ответ и безопасное сообщение об ошибке.
- Добавлены четыре component-теста: успешный ответ, ошибка сети, безопасная
  HTTP-ошибка и запрет отправки пустой строки.
- Trace и approval намеренно не добавлены: они относятся к следующим
  микроэтапам.

#### Зачем это нужно

Мы получили самый маленький законченный путь от браузера до существующего
агента. Теперь frontend уже полезен сам по себе, но остаётся достаточно простым,
чтобы отдельно увидеть границу ответственности между React и backend.

#### Как это работает простыми словами

Пользователь вводит просьбу. React сохраняет её в локальном диалоге, временно
блокирует повторную отправку и делает один HTTP-запрос. Backend создаёт agent
run, сам выбирает и безопасно вызывает нужные tools, сохраняет результат и
возвращает run. Если run завершён, React показывает `final_answer`. Если запрос
оборвался, `finally` снимает loading, а пользователь видит безопасную ошибку и
может попробовать ещё раз.

#### На что обратить внимание

- React не знает, какой tool понадобится, и не дублирует agent loop.
- Текст в форме и признак активной отправки являются локальным UI state; сам
  run принадлежит серверу.
- Текущий loading означает ожидание единственного HTTP-ответа, а не streaming.
- В DTO нет trace, pending approval и внутренних backend-полей, потому что
  экран 7.1 их не использует.
- Для одного запроса достаточно локального состояния; отдельный state manager
  пока только усложнил бы код.

#### Как проверено

- `npm test`: 4 component-теста пройдены.
- `npm run build`: TypeScript и production bundle собраны успешно.
- `npm run lint`: замечаний нет.
- `uv run pytest -q` из `backend/`: 185 backend-тестов пройдены.
- Browser smoke: реальный запрос прошёл через dev proxy и вернул ответ backend.
- Mobile smoke на 390 × 844: горизонтального скролла нет.
- Контраст активной кнопки: 4,95:1.

#### Что мы выучили

Первый frontend-срез не обязан сразу отображать всю модель данных. Полезнее
начать с одного законченного пользовательского действия, явно разделить
локальное состояние интерфейса и серверный run, а затем расширять публичный
контракт только под следующий проверяемый сценарий.

#### Советы на будущее

- Перед обновлением UI сначала определить новое состояние backend и его
  публичный DTO.
- Для запуска frontend использовать поддерживаемую версию Node.js.
- Не смешивать в одном микроэтапе базовый запрос, trace и approval: у них разные
  состояния, риски и проверки.
- Ответы на контрольные вопросы этого микроэтапа зафиксированы в разделе
  «Самоконтроль» выше.

## 7.2. Карта состояний run и безопасный trace

### Результат итерации

Интерфейс различает `completed`, `failed`, `step_limit_exceeded` и
`waiting_for_approval`, показывает причину остановки и учебный trace без сырых
messages, secrets и внутренних исключений.

### Что реализуем

- Расширим frontend DTO полным публичным контрактом `AgentRunResponse`.
- Введём явное отображение каждого серверного статуса.
- Покажем номер шага, длительность, имя предложенного tool и наличие результата.
- Сформируем allowlist данных trace, допустимых для пользовательского экрана.
- Не будем выводить сырые `messages`, arguments, provider payload и внутреннее
  поле exception.
- Добавим component-тест каждого состояния и негативный тест неизвестного
  значения на границе декодирования.

### Зачем это нужно

Одинаковая карточка для всех исходов скрыла бы принципиальную разницу между
успехом, ошибкой, лимитом и безопасной паузой. При этом прямой вывод всего JSON
trace раскрыл бы детали, которые создавались для отладки backend, а не для
пользователя.

### Как это должно работать простыми словами

Backend уже сообщает, чем закончился запуск. React не угадывает состояние по
тексту ответа, а выбирает представление по структурированному `status`. Для
учебной прозрачности пользователь видит краткую цепочку шагов, но только те
поля, которые заранее признаны безопасными.

### На что обратить внимание

- `waiting_for_approval` не является ошибкой или завершением.
- `step_limit_exceeded` должен объяснять остановку, а не выглядеть как вечный
  loading.
- `error` backend может содержать техническую классификацию и не всегда годится
  для прямого показа.
- Название tool полезно для обучения, но arguments могут содержать внутренние
  идентификаторы или будущие чувствительные данные.
- Не следует строить UI по наличию `final_answer`, игнорируя `status`.

### Проверка

- Component: каждый известный status получает отдельный понятный заголовок.
- Component: tool call отображает только разрешённые поля.
- Негативный: trace с внутренними messages/arguments не выводит их текст.
- Негативный: неизвестный status превращается в контролируемую ошибку контракта.
- Regression: completed-сценарий 7.1 сохраняет прежнее поведение.

### Критерий готовности

По экрану можно однозначно понять причину остановки run и его безопасные шаги,
не открывая DevTools. Запрещённые поля trace отсутствуют в DOM, тесты и отчёт
готовы, итерация зафиксирована отдельным коммитом.

### Самоконтроль

**Почему нельзя определять успех по наличию красивого текста модели?**

Модель способна написать убедительный ответ даже после ошибки tool. Бизнес-
контрактом являются status, stop reason и сохранённые результаты, а не стиль
свободного текста.

**Зачем показывать trace, если пользователь уже получил ответ?**

Проект учебный: краткий trace помогает увидеть связь между целью, решением
модели и инструментом. Но он остаётся представлением публичных данных, а не
дампом внутренних объектов.

**Какие данные trace опасно показывать автоматически?**

Полные prompts, provider payload, stack traces, headers, произвольные arguments
и необработанные tool errors. Сегодня они могут быть безобидны, но контракт
экрана не должен предполагать это навсегда.

### Совет на будущее

Если безопасное представление шага станет сложным, лучше добавить отдельный
backend DTO для UI, чем учить React фильтровать постоянно меняющийся внутренний
trace.

### Отчёт о завершении 7.2

#### Что сделано

- Описан полный публичный `AgentRunResponse`, включая working state, pending
  action и сохранённые шаги.
- Добавлен runtime decoder между неизвестным JSON и React. Он принимает только
  известные статусы и строит отдельную безопасную UI-модель.
- Для `running`, `waiting_for_approval`, `completed`, `failed` и
  `step_limit_exceeded` добавлены отдельные заголовки и объяснения.
- Учебный trace показывает только номер шага, длительность, имена tools и
  количество результатов.
- `messages`, arguments, provider text, содержимое tool results и внутренние
  ошибки отбрасываются до передачи данных компонентам.
- Trace сделан раскрываемым через нативный `details`, поэтому он доступен с
  клавиатуры и не перегружает основной ответ.

#### Зачем это нужно

Пользователь теперь видит реальный исход запуска, а не пытается угадать его по
тексту модели. Одновременно учебная прозрачность не превращается в публикацию
полного отладочного JSON.

#### Как это работает простыми словами

Backend возвращает большой объект run. Decoder сначала проверяет status и
форму необходимых полей. Затем он словно пропускает каждый шаг через сито:
оставляет номер, время, название tool и количество результатов, а всё
внутреннее выбрасывает. React получает уже безопасный объект и выбирает
представление строго по status.

#### На что обратить внимание

- Красивый финальный текст не доказывает успех. Источником истины является
  структурированный status.
- `waiting_for_approval` обозначает безопасную паузу, а не ошибку.
- `step_limit_exceeded` является законченным исходом и не оставляет loading.
- Неизвестный status не угадывается: пользователь получает контролируемую
  ошибку контракта.
- Backend error и stop reason намеренно не выводятся как произвольный текст.
- Типографские длинные тире из динамического ответа нормализуются перед выводом.

#### Как проверено

- `npm test`: 11 component-тестов пройдены.
- Тестами покрыты все пять известных статусов и неизвестный status.
- Негативный тест доказывает отсутствие messages, arguments, tool output и
  внутреннего exception в DOM.
- `npm run build`: TypeScript и production bundle собраны успешно.
- `npm run lint`: замечаний нет.
- `uv run pytest -q` из `backend/`: 185 backend-тестов пройдены.
- Browser smoke: реальный completed-run показал два безопасных шага trace.
- Mobile smoke на 390 × 844: горизонтального скролла нет.

#### Что мы выучили

TypeScript-интерфейс сам по себе не проверяет JSON во время выполнения. Между
API и UI нужна явная граница декодирования. Безопаснее создавать новый объект
из разрешённых полей, чем передавать полный ответ дальше и надеяться, что
компонент случайно не выведет лишнее.

#### Советы на будущее

- При добавлении нового server status сначала обновлять decoder и тест
  исчерпывающего отображения.
- Если frontend понадобится больше деталей trace, расширять allowlist одним
  обоснованным полем, а не открывать весь объект.
- Представление pending action реализовать отдельно в 7.3, не добавляя кнопки
  approve/reject раньше микроэтапа 7.4.
- Ответы на контрольные вопросы этого микроэтапа зафиксированы в разделе
  «Самоконтроль» выше.

## 7.3. Отображение ожидающего подтверждения

### Результат итерации

Run в `waiting_for_approval` показывает отдельную карточку с backend summary,
сроком действия и объяснением последствий. Кнопки решения пока не отправляют
запрос: эта итерация проверяет только правильное представление границы доверия.

### Что реализуем

- Создадим approval-карточку для `pending_action.status == pending`.
- Покажем безопасный `summary` и понятное время истечения.
- Свяжем карточку с конкретными run ID и action ID внутри состояния, не выводя
  технические идентификаторы как основной текст.
- Не будем отображать или редактировать сохранённые arguments.
- Добавим состояния истёкшего времени на клиенте только как подсказку; итоговое
  решение о просрочке остаётся за backend.
- Добавим component-тест pending-карточки и негативный тест отсутствующего
  `pending_action` при статусе ожидания.

### Зачем это нужно

Перед реализацией мутации полезно отдельно доказать, что пользователь видит
именно тот объект и последствия, которые подготовил backend. Так ошибки
представления не смешиваются с ошибками approve/reject orchestration.

### Как это должно работать простыми словами

Backend останавливается до удаления и присылает готовое описание действия.
React показывает это описание как отдельное решение, а не как обычный ответ
чата. Пользователь понимает, что ничего ещё не удалено и что решение имеет срок.

### На что обратить внимание

- Summary является доверенным описанием backend, но всё равно выводится как
  обычный текст, а не HTML.
- Истечение таймера в браузере не изменяет запись в БД.
- Нельзя реконструировать arguments из текста summary.
- Отсутствующий pending при `waiting_for_approval` означает нарушение контракта,
  а не пустое успешное состояние.
- Карточка должна быть доступна с клавиатуры и понятна без одного лишь цвета.

### Проверка

- Component: waiting-run показывает summary и срок.
- Component: arguments и внутренние ключи не появляются в DOM.
- Негативный: waiting без pending даёт контролируемое сообщение о несогласованном
  ответе.
- Accessibility: заголовок и описание карточки связаны семантически.
- Regression: остальные статусы продолжают использовать представления 7.2.

### Критерий готовности

Пользователь может своими словами объяснить, какое действие предлагается и что
оно ещё не выполнено. Карточка не принимает решение, не раскрывает arguments и
покрыта тестами; написан отчёт и отдельный коммит.

### Самоконтроль

**Почему summary нельзя заново строить во frontend по имени tool?**

React не владеет доменными данными и может назвать не тот объект или пропустить
важное последствие. Backend уже связал validated arguments с реальной записью и
сформировал описание в доверенном контексте.

**Почему клиентский таймер не должен сам помечать action как expired?**

Часы браузера могут отличаться, вкладка может спать, а другой процесс уже мог
принять решение. Только backend атомарно знает сохранённый статус и применяет
правило срока действия.

**Зачем отделять показ карточки от реализации кнопок?**

Это уменьшает число неизвестных: сначала проверяется предмет человеческого
согласия, затем отдельно семантика мутации, повторов и ошибок решения.

### Совет на будущее

Не превращать approval summary в универсальную форму редактирования arguments.
Если пользователю нужно изменить действие, безопаснее отклонить текущее и
сформулировать новую цель агенту.

### Отчёт о завершении 7.3

#### Что сделано

- Safe UI-модель run расширена полем pending action с action ID, summary и
  временем истечения.
- Decoder требует pending action со статусом `pending` для каждого
  `waiting_for_approval`. Отсутствующее или несогласованное действие считается
  ошибкой контракта.
- Добавлена отдельная семантическая approval-карточка с заголовком, summary,
  объяснением последствий и понятным сроком.
- Run ID и action ID сохраняются в состоянии для следующего микроэтапа, но не
  показываются как пользовательский текст.
- Карточка намеренно не содержит кнопок и не отправляет approve/reject.
- Клиентская подсказка меняется на истёкшее состояние по таймеру, но ничего не
  записывает в backend.
- Datetime без timezone, полученный из SQLite, трактуется как UTC. Это устраняет
  ложное мгновенное истечение в московском часовом поясе.

#### Зачем это нужно

Пользователь должен увидеть предмет согласия до появления настоящей мутации.
Теперь интерфейс ясно сообщает, какое действие подготовлено, что оно ещё не
выполнено и сколько времени backend разрешает принять решение.

#### Как это работает простыми словами

Agent loop доходит до удаления и останавливается. Backend сохраняет проверенное
действие и присылает готовое описание. Decoder проверяет связанный pending
action, а React показывает summary как обычный текст. Таймер в браузере лишь
обновляет подсказку о сроке; удалить книгу или изменить серверный статус он не
может.

#### На что обратить внимание

- Summary формирует backend, потому что именно он знает проверенные arguments и
  реальный объект действия.
- React не реконструирует summary по имени tool и не показывает arguments.
- Истёкший клиентский таймер является подсказкой. Окончательное решение о сроке
  принимает backend.
- Action ID нужен для будущего URL решения, но не является главным содержимым
  карточки.
- Далёкий срок разбивается на безопасные интервалы, чтобы не переполнить
  ограничение браузерного `setTimeout`.

#### Как проверено

- Негативный тест покрывает waiting-run без pending action.
- Тест истёкшего срока подтверждает, что новый HTTP-запрос не отправляется.
- Тест доказывает отсутствие arguments, idempotency key и технических ID в

#### Что мы выучили

Approval начинается не с кнопки, а с точного и безопасного описания предмета

браузер и backend могут понять её по-разному. Такие значения нужно

#### Советы на будущее

- В 7.4 строить approve/reject URL только из сохранённых run ID и action ID.
- Не отправлять обратно summary или arguments вместе с решением.

  браузера.

## 7.4. Approve, reject и защита от повторного решения

### Результат итерации

Пользователь может явно подтвердить или отклонить pending action. Во время
решения обе кнопки заблокированы, двойной клик не создаёт второй HTTP-запрос, а
результат возобновлённого run заменяет ожидающее состояние.

### Что реализуем

- Добавим типизированные методы approve и reject в API client.
- Будем строить URL только из сохранённых run ID и action ID.
- Отправим пустое JSON-тело без arguments и summary.
- Введём единое локальное состояние `decision_in_flight` для обеих кнопок.
- После ответа заменим активный run значением `ApprovalResponse.run`.
- Отобразим replayed-ответ как тот же итог, не запуская новую мутацию.
- Покроем approve, reject, двойной клик, `409` и `410` component/integration-
  тестами API client.

### Зачем это нужно

Approval становится настоящим пользовательским действием. Основной риск
frontend здесь не в удалении как таковом, а в повторной доставке, подмене
arguments и неправильном отображении конфликта уже принятого решения.

### Как это должно работать простыми словами

Пользователь нажимает одну из двух явных кнопок. React сразу блокирует обе,
чтобы второе решение не ушло параллельно. Backend находит ранее сохранённое
действие, сам исполняет или отклоняет его и продолжает тот же run. В ответ React
получает уже новое состояние процесса и показывает его вместо карточки ожидания.

### На что обратить внимание

- Approve/reject endpoint не принимает новые arguments.
- Блокировка одной кнопки обязана блокировать и противоположную.
- Клиентская защита от двойного клика улучшает UX, но единственное исполнение
  по-прежнему гарантирует backend.
- `409 Conflict` означает устаревшее или уже принятое решение, а `410 Gone` —
  просроченное; это не одинаковые ошибки сети.
- Повторный успешный ответ с `replayed=true` не является новым выполнением.

### Проверка

- Component: approve отправляет ровно один запрос с пустым телом.
- Component: reject отправляет правильный endpoint и не вызывает approve.
- Негативный: двойной клик создаёт один запрос.
- Component: обе кнопки disabled, пока решение выполняется.
- API client: `409` и `410` преобразуются в понятные контролируемые состояния.
- Regression: pending summary остаётся видимым до получения ответа backend.

### Критерий готовности

Approve и reject проходят через UI, не передают замену arguments и корректно
показывают возобновлённый run. Повторное нажатие не создаёт второй запрос;
готовы тесты, учебный отчёт и отдельный коммит.

### Самоконтроль

**Почему disabled-кнопка во frontend не доказывает единственное исполнение?**

Запрос можно повторить из другой вкладки, после timeout или напрямую через
HTTP. React уменьшает случайные повторы, но атомарность и идемпотентность
принадлежат backend.

**Почему approve не отправляет summary обратно?**

Summary нужен человеку для чтения, но не является исполняемым контрактом.
Backend уже сохранил validated arguments и обязан использовать именно их.

**Как интерфейс должен трактовать `replayed=true`?**

Как безопасное повторное чтение уже принятого результата. Пользователь видит
итоговый run, но UI не сообщает, будто действие выполнено второй раз.

### Совет на будущее

Не добавлять optimistic deletion книги до ответа backend. Для destructive-
действия правильнее сначала получить подтверждённый результат, а затем обновить
библиотеку из источника истины.

### Отчёт о завершении 7.4

#### Что сделано

- В API client добавлен единый типизированный метод решения с вариантами
  `approve` и `reject`.
- Endpoint строится только из сохранённых run ID и action ID. В body уходит
  ровно пустой JSON `{}` без summary и arguments.
- Ответ approval проходит runtime decoder и возвращает безопасный run вместе с
  признаком `replayed`.
- В карточку добавлены две явные кнопки решения.
- Единое состояние `decision_in_flight` блокирует обе кнопки, а синхронный lock
  не пропускает второй запрос до React rerender.
- Pending-run остаётся на экране во время запроса и заменяется ответом backend
  только после успеха.
- `replayed=true` отображается как обычный итоговый run без сообщения о новом
  повторном выполнении.
- `409` и `410` получили разные безопасные объяснения; после ошибки карточка
  остаётся доступной.
- На мобильном кнопки складываются в одну колонку, чтобы подписи не
  сталкивались.

#### Зачем это нужно

Теперь human-in-the-loop проходит полный пользовательский цикл: человек видит
подготовленное действие, явно принимает решение и получает продолжение того же
run. Frontend при этом не может заменить сохранённые backend arguments.

#### Как это работает простыми словами

При нажатии React сразу закрывает обе кнопки для повторного решения и отправляет
backend только адрес сохранённого действия и выбранный глагол. Backend сам
берёт проверенные arguments, атомарно принимает решение и продолжает agent loop.
Когда новый run возвращается, React заменяет им ожидающую карточку. При ошибке
карточка остаётся, а пользователь видит понятную причину.

#### На что обратить внимание

- Disabled-кнопки защищают от случайного двойного клика только в этой вкладке.
  Единственное исполнение по-прежнему гарантирует backend.
- Summary является текстом для человека и никогда не отправляется как команда.
- Approve и reject используют одинаковую блокировку, поэтому противоположное
  решение нельзя отправить параллельно.
- `409` означает конфликт уже изменившегося состояния, а `410` сообщает об
  истёкшем сроке.
- Optimistic deletion не используется: библиотека меняется только после ответа
  источника истины.

#### Как проверено

- `npm test`: 19 component/integration-тестов пройдены.
- Approve отправляет один POST с body `{}` и заменяет waiting-run.
- Reject использует отдельный endpoint и не вызывает approve.
- Двойной клик создаёт только один запрос решения.
- Во время запроса обе кнопки disabled, а summary остаётся видимым.
- `409` и `410` показывают разные сообщения без внутренних backend details.
- `replayed=true` показывает тот же итоговый run.
- `npm run build`: TypeScript и production bundle собраны успешно.
- `npm run lint`: замечаний нет.
- `uv run pytest -q` из `backend/`: 185 backend-тестов пройдены.
- Browser smoke: реальный reject заблокировал обе кнопки, продолжил run и
  сохранил книгу в библиотеке.
- Mobile smoke на 390 × 844: горизонтального скролла нет, кнопки не
  пересекаются.

#### Что мы выучили

Frontend-блокировка и backend-идемпотентность решают разные задачи. Первая
делает интерфейс предсказуемым, вторая гарантирует корректность при повторах из
другой вкладки, после timeout или напрямую через HTTP. Для destructive-действия
UI должен передавать решение, а не пересобирать исполняемые данные.

#### Советы на будущее

- В 7.5 после refresh перечитывать run с backend, а не повторять POST решения.
- После `409/410` восстановление сможет запросить актуальный run и убрать
  устаревшую карточку.
- Не хранить approval response как авторитетную копию вне текущей сессии.
- Ответы на контрольные вопросы этого микроэтапа зафиксированы в разделе
  «Самоконтроль» выше.

## 7.5. Восстановление run после перезагрузки

### Результат итерации

Если страница обновлена во время `waiting_for_approval`, интерфейс перечитывает
тот же run с backend и снова показывает актуальную approval-карточку. Завершённое
или несуществующее состояние обрабатывается предсказуемо.

### Что реализуем

- Сохраним в versioned localStorage-схеме только ID активного незавершённого run.
- При старте вызовем `GET /api/agent/runs/{run_id}`.
- Покажем отдельное loading-состояние восстановления, не создавая новый run.
- После `404` удалим устаревшую локальную ссылку и откроем новую пустую сессию.
- После terminal status очистим ссылку на незавершённый процесс.
- Не будем сохранять pending summary, arguments, trace или итог библиотеки как
  авторитетную копию.
- Добавим integration-тест с размонтированием и новым render приложения.

### Зачем это нужно

Human-in-the-loop почти всегда переживает границу одного HTTP-запроса и может
длиться дольше жизни вкладки. Без восстановления безопасная пауза существует в
БД, но пользователь теряет способ принять решение после обычного refresh.

### Как это должно работать простыми словами

Браузер запоминает не весь процесс, а только его номер. После перезагрузки он
просит backend показать актуальное состояние этого номера. Поэтому решение,
принятое в другой вкладке, просрочка или изменение run сразу отражаются в UI, а
старый локальный снимок не вводит пользователя в заблуждение.

### На что обратить внимание

- localStorage является подсказкой навигации, а не базой данных.
- Схема сохранённого значения должна иметь версию и строгую проверку формы.
- Повреждённый JSON не должен ломать загрузку всего приложения.
- Нельзя автоматически повторять `POST /agent/runs` после refresh.
- GET run уже ограничен demo user на backend; в будущем это станет частью
  настоящей авторизации.

### Проверка

- Integration: waiting-run сохраняет ID, новый render вызывает GET и
  восстанавливает ту же карточку.
- Негативный: повреждённое localStorage-значение очищается без crash.
- Негативный: `404` очищает ссылку и показывает пустую сессию.
- Integration: terminal run не остаётся помеченным как незавершённый.
- Regression: восстановление не вызывает LLM provider и не создаёт новый run.

### Критерий готовности

Refresh в состоянии ожидания не теряет процесс и не дублирует agent run.
Backend остаётся источником истины, негативные случаи покрыты, написан отчёт и
создан отдельный коммит.

### Самоконтроль

**Почему нельзя сохранить весь `AgentRunResponse` в localStorage и показать его
без GET?**

Этот снимок устаревает: решение могло быть принято в другой вкладке, action мог
просрочиться, а run — завершиться. ID позволяет найти актуальное состояние, не
создавая конкурирующую копию истины.

**Почему refresh не должен повторять исходный POST?**

POST создаёт новый run и способен повторить write-tools. Восстановление означает
чтение уже существующего процесса по ID, а не повтор пользовательской команды.

**Зачем версионировать маленькое localStorage-значение?**

Даже простая форма со временем меняется. Версия позволяет безопасно отвергнуть
старый формат вместо неявной ошибки при чтении.

### Совет на будущее

При появлении настоящих аккаунтов ключ хранения должен учитывать пользователя,
а logout обязан очищать локальную ссылку. На demo-user этапе не нужно заранее
строить универсальный session store.

## 7.6. Библиотека и четыре MVP-сценария

### Результат итерации

Пользователь видит текущую библиотеку в интерфейсе и может пройти четыре
сценария проекта без ручного curl: просмотр, добавление книги, изменение статуса
и многошаговую рекомендацию. После write/destructive-run библиотека перечитывается
с backend.

### Что реализуем

- Добавим типизированный `GET /api/library` в API client.
- Покажем книги, авторов и статусы чтения в компактном доступном представлении.
- Реализуем loading, empty и error для библиотеки независимо от чата.
- После terminal run с выполненными write/destructive tools заново запросим
  библиотеку.
- Не будем оптимистично вычислять изменения по тексту модели.
- Добавим интеграционные UI-сценарии четырёх MVP-команд с scripted API.
- Добавим один настоящий E2E smoke «поиск → добавление → книга видна» через
  локальные frontend и backend с fake provider.

### Зачем это нужно

Красивый ответ модели не доказывает бизнес-результат. Библиотека делает эффект
видимым через отдельное чтение доменного состояния и замыкает пользовательский
цикл без DevTools и ручных API-команд.

### Как это должно работать простыми словами

После запуска агент может добавить книгу или изменить её статус. Когда run
заканчивается, React не пытается угадать новый список по фразе модели, а снова
запрашивает библиотеку. Пользователь видит фактические данные, сохранённые в БД.

### На что обратить внимание

- Chat response и библиотека являются разными server-state ресурсами.
- Нельзя считать любой completed-run изменяющим данные; completed может быть
  только чтением.
- Повторный GET безопаснее optimistic update для первого MVP.
- Большой catalog search UI не входит в этап: пользователь взаимодействует с
  каталогом через агента.
- E2E с fake provider проверяет wiring и эффекты, но не качество реальной LLM.

### Проверка

- Component: loading, empty, populated и error-состояния библиотеки.
- Integration: completed write-run вызывает refresh и показывает новые данные.
- Негативный: failed-run не рисует выдуманное изменение.
- MVP: просмотр reading, добавление, смена статуса и рекомендация проходят через
  UI с детерминированным provider.
- E2E smoke: добавленная книга присутствует в ответе настоящего library API.

### Критерий готовности

Все четыре MVP-сценария доступны в браузере, а результат write-сценария
подтверждается перечитанной библиотекой. Тесты, отчёт и отдельный коммит готовы.

### Самоконтроль

**Почему финальный ответ «Книга добавлена» недостаточен для обновления UI?**

Это свободный текст модели. Tool мог завершиться ошибкой или изменить другой
объект. Фактическим доказательством служит состояние library API.

**Что доказывает E2E с fake provider?**

Он доказывает работу браузера, HTTP-контрактов, agent orchestration и БД как
одной системы. Он не доказывает, что реальная модель всегда выберет правильную
последовательность tools.

**Почему библиотеку можно обновлять повторным GET вместо сложного cache update?**

Данных мало, запрос локальный и детерминированный, а повторное чтение исключает
расхождение с backend. Более сложный cache нужен только при измеримой проблеме.

### Совет на будущее

Если библиотека станет большой, сначала добавить пагинацию и измерить задержку.
Не вводить нормализованный глобальный cache до появления такого требования.

## 7.7. Доступность, E2E и закрытие этапа

### Результат итерации

Полный пользовательский MVP работает с клавиатуры на desktop и mobile,
восстанавливает approval после refresh, не допускает двойного решения и ясно
объясняет каждый конечный статус. Frontend и backend regression зелёные,
документация отражает фактический результат.

### Что реализуем

- Проведём keyboard-аудит формы, trace, approval и библиотеки.
- Проверим focus order, focus-visible, labels, live regions и семантические
  заголовки.
- Проверим contrast, reduced motion, light/dark theme и mobile breakpoints.
- Добавим сквозные acceptance-сценарии approve и reject с перезагрузкой страницы.
- Проверим ошибку API, двойной клик и восстановление после `404`.
- Выполним полный frontend и backend regression, production build и schema
  check.
- Обновим README, основной roadmap и этот документ полноценным финальным
  отчётом этапа.

### Зачем это нужно

Отдельные зелёные компоненты ещё не гарантируют рабочий процесс. Финальный
checkpoint проверяет границы между вкладкой, HTTP, новым backend session,
approval и доменными данными, а также делает интерфейс пригодным не только для
мыши и одного размера экрана.

### Как это должно работать простыми словами

Мы повторяем действия реального пользователя от первого сообщения до видимого
изменения библиотеки, включая паузу и обновление страницы. Затем проверяем тот
же путь в неудобных условиях: клавиатура, узкий экран, ошибка сервера и повторный
клик. Только после этого этап считается пользовательским MVP.

### На что обратить внимание

- Accessibility нельзя полностью доказать snapshot-тестом; нужен ручной проход.
- E2E не должен зависеть от реальной сети или формулировки LLM.
- Assertions строятся по status, summary, DOM и данным БД, а не по точной фразе
  финального ответа.
- Не следует добавлять streaming в финальный checkpoint: он изменит транспорт и
  расширит область проверки без необходимости для MVP.
- Документация обновляется только после фактического прохождения всех критериев.

### Проверка

- Frontend: component/integration/E2E suite полностью проходит.
- Backend: полный pytest regression проходит.
- Build/lint: production bundle и статические проверки зелёные.
- Alembic: рабочая и чистая база находятся на head, schema check чистый.
- Browser: desktop, mobile, light, dark, keyboard и reduced motion проверены.
- Acceptance approve: после refresh действие исполняется один раз.
- Acceptance reject: после refresh библиотека не изменяется.

### Критерий готовности

Выполнены все критерии этапа 7 из основного roadmap. Четыре MVP-сценария и оба
approval-решения доступны без ручного API; refresh восстанавливает pending;
причина остановки видна; frontend не содержит выбора tools. Написан финальный
учебный отчёт и создан отдельный checkpoint-коммит.

### Самоконтроль

**Что в этой системе принадлежит frontend, а что backend?**

Frontend владеет вводом, фокусом, временным loading и способом отображения.
Backend владеет run, выбором tools, validation, approval policy, эффектами,
trace и доменными данными.

**Что streaming изменит, а чего не изменит?**

Он может раньше показать текст или события и улучшить ощущение скорости. Он не
переносит agent loop в React, не меняет approval policy и не становится
источником истины для состояния run.

**Почему этап нельзя закрыть только зелёными component-тестами?**

Они изолируют UI от настоящих HTTP, process/session и БД границ. Ошибка может
появиться только при перезагрузке, проксировании, миграции или совместной работе
нескольких endpoints.

**Какие данные нельзя показывать без фильтрации даже в учебном trace?**

Secrets, headers, полные prompts, stack traces, внутренние provider payload,
произвольные arguments и необработанные ошибки зависимостей.

### Совет на будущее

После checkpoint отдельно измерить, где синхронный UX действительно мешает.
Только затем выбирать streaming-транспорт и добавлять observability для него,
сохраняя уже доказанные границы run и approval.

## Финальный checkpoint этапа 7

Перед переходом к внешнему каталогу и PostgreSQL должно быть доказано:

- пользователь создаёт run из браузера и видит финальный ответ;
- все конечные статусы различимы и имеют понятную причину;
- trace показывает безопасный allowlist, а не внутренний дамп;
- approval summary приходит от backend и не реконструируется в React;
- approve/reject не передают replacement arguments;
- двойной клик не создаёт два клиентских запроса, а backend сохраняет
  единственное исполнение;
- pending action восстанавливается после refresh через GET существующего run;
- четыре MVP-сценария доступны без curl;
- результат write/destructive-действия подтверждается состоянием библиотеки;
- keyboard, mobile, light/dark и ошибки API проверены;
- frontend, backend, E2E и миграционные проверки проходят;
- после каждой итерации существует отдельный коммит и учебный отчёт.
