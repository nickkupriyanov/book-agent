# Этап 8: микро-роадмап

Этот документ разбивает этап «Внешний каталог и PostgreSQL» на небольшие
проверяемые итерации. Мы проходим их строго по порядку. После каждой итерации
приложение остаётся рабочим, а все ранее реализованные сценарии продолжают
проходить.

Вернуться к общей карте: [ROADMAP.md](./ROADMAP.md).

## Граница этапа

Целевой пользовательский процесс:

1. пользователь просит агента найти реальную книгу;
2. backend ищет произведения через Open Library и нормализует внешний payload;
3. найденные произведения получают устойчивые внутренние UUID и сохраняются;
4. пользователь может добавить найденную книгу прежним `add_book`;
5. повторный поиск не создаёт дубликат;
6. временная ошибка каталога ограниченно повторяется и приводит к локальному
   fallback;
7. источник, cache hit и деградация видны в безопасном trace;
8. тот же backend работает на чистой PostgreSQL и в SQLite-тестах.

На этом этапе мы не строим универсальный federation/search engine, не
объединяем результаты нескольких внешних поставщиков, не переносим старую
SQLite-базу, не добавляем фоновые очереди обновления каталога и не считаем ISBN
идентичностью произведения.

## Принятые решения

- Внешний поставщик — Open Library Search API, сущность — work.
- Поиск работает по правилу external-first; local catalog используется только
  при деградации или когда явно выбран local provider.
- Внутренний UUID детерминированно строится из `open_library + work_id`.
- ISBN — необязательная метаинформация одного издания, а не ключ произведения.
- Успешные запросы попадают в небольшой in-memory TTL-кэш, найденные книги — в
  БД до возврата результата.
- PostgreSQL поднимается с нуля миграциями и seed; SQLite остаётся быстрым
  тестовым вариантом.
- Backend формирует структурированные `source`, `degraded` и `cached`; модель
  и frontend не угадывают фактический путь выполнения.

## Рабочий договор для каждой итерации

Каждый микроэтап заканчивается отдельным коммитом и учебным отчётом:

1. **Что сделано:** новый поток данных и наблюдаемый результат.
2. **Зачем:** устранённая проблема, риск или неопределённость.
3. **На что обратить внимание:** инварианты, границы доверия и компромиссы.
4. **Как проверено:** тесты, команды и фактический результат.
5. **Что мы выучили:** переносимые инженерные принципы.
6. **Советы на будущее:** что пока не следует усложнять.
7. **Самоконтроль:** содержательные вопросы и ответы своими словами.

Если критерий готовности не выполнен, негативный сценарий не проверен или нет
ответов на самоконтроль, микроэтап не считается завершённым.

## 8.1. Контракт каталога и локальная реализация

### Результат итерации

`BookService` ищет через внедрённый `BookCatalog`, а текущая локальная реализация
сохраняет прежнее поведение API, tools и рекомендаций.

### Что реализуем

- Введём каталожные DTO, `CatalogSearchResult` и протокол `BookCatalog`.
- Перенесём текущий поиск в `LocalBookCatalog`.
- Оставим repository ответственным только за хранение.
- Подключим каталог через FastAPI dependency injection.

### Проверка и критерий готовности

- Общий contract-тест каталога проходит для local-реализации.
- Пустой запрос отклоняется на публичной границе.
- Все прежние backend-тесты проходят без изменения agent loop и tool arguments.

### Самоконтроль с ответами

**Почему каталог не равен repository?** Каталог описывает источник и семантику
поиска, repository — сохранение и чтение состояния приложения.

**Почему контракт вводится до HTTP-клиента?** Внешний формат тогда остаётся за
адаптером и не формирует интерфейсы сервиса и tools.

**Что доказывает local-реализация?** Источник поиска можно заменить без
изменения пользовательского сценария и agent loop.

### Отчёт о завершении 8.1

**Что сделано.** Добавлены независимые каталожные DTO, протокол `BookCatalog` и
`LocalBookCatalog`. `BookService` получает каталог через конструктор, а
совместимый `search_books` пока разворачивает новый результат в прежний список.

**Зачем.** Поиск больше не является скрытой обязанностью repository. Появилась
явная точка замены источника до добавления HTTP и внешнего payload.

**На что обратить внимание.** Catalog DTO не является ORM-моделью. Agent loop,
tool arguments и HTTP-ответы не изменились; default local catalog сохранён для
простых unit-тестов сервиса.

**Как проверено.** Contract-тест подтвердил source-флаги, Unicode-поиск и
отклонение пустого запроса/неверного limit. Полный backend suite прошёл.

**Что мы выучили.** Dependency inversion полезен тогда, когда отделяет две уже
разные ответственности, а не добавляет абстракцию ради будущего имени.

**Советы на будущее.** Не переносить persistence и retry в протокол каталога:
это отдельные части следующего потока.

## 8.2. Open Library: транспорт и нормализация

### Результат итерации

Изолированный адаптер выполняет Search API-запрос и преобразует допустимые work
documents в стабильные каталожные DTO.

### Что реализуем

- GET `/search.json` с полями `key,title,author_name,isbn,cover_i,subject_key`.
- Отдельные HTTP-транспорт и чистую нормализацию payload.
- Нормализацию work ID, пробелов, авторов, ISBN, cover URL и ограниченного
  стабильного набора тегов.
- Пропуск повреждённых документов и поддержку отсутствующих необязательных
  полей.

### Проверка и критерий готовности

- Fixture-тесты покрывают несколько авторов и отсутствующие ISBN/обложку.
- Повреждённый document пропускается, неверный корневой payload даёт
  контролируемую ошибку.
- Основной test suite не выполняет сетевых запросов.

### Самоконтроль с ответами

**Где преобразуется внешний payload?** Только внутри anti-corruption boundary
адаптера.

**Почему payload нельзя передавать прямо модели?** Его форма нестабильна и
содержит больше данных, чем разрешает внутренний контракт.

**Почему work ID важнее ISBN?** Work описывает произведение, а ISBN относится к
изданию и может отсутствовать.

### Отчёт о завершении 8.2

**Что сделано.** Добавлены HTTP-транспорт с явными query fields и User-Agent,
Open Library catalog и чистый normalizer work documents.

**Зачем.** Сетевые детали и нестабильный payload изолированы от домена до
подключения внешнего поиска к пользовательскому сценарию.

**На что обратить внимание.** Work без валидных key/title пропускается;
авторы, ISBN, cover и subjects необязательны. ISBN-13 выбирается прежде ISBN-10,
но не участвует в идентичности.

**Как проверено.** Детерминированные тесты проверили URL, fields, User-Agent,
несколько авторов, отсутствующие поля, повреждённые documents, invalid JSON и
корневой payload. Полный backend suite прошёл без сети.

**Что мы выучили.** Anti-corruption layer должен превращать внешний ответ в
маленькую внутреннюю модель до того, как данные увидят сервисы или LLM.

**Советы на будущее.** Не добавлять второй provider и edition API, пока work
search не доказан сквозным сценарием.

## 8.3. Сохранение и дедупликация внешних книг

### Результат итерации

Каждая возвращённая внешняя книга уже существует в БД, а повторный или
конкурентный поиск одного work не создаёт второй записи.

### Что реализуем

- Добавим поля источника, external ID, ISBN, cover URL и времени обновления.
- Добавим уникальность `(catalog_source, external_id)`.
- Сохраним прежние UUID seed-книг и отметим их источником `local`.
- Реализуем атомарный upsert нормализованных результатов перед возвратом.

### Проверка и критерий готовности

- Повторная и конкурентная выдача возвращают один внутренний UUID.
- Существующие library entries переживают миграцию.
- Внешняя книга добавляется прежним `add_book` без нового аргумента.

### Самоконтроль с ответами

**Зачем разделять внутренний и внешний ID?** Внутренние связи не должны зависеть
от формата и жизненного цикла поставщика.

**Почему title не годится для уникальности?** Названия повторяются, переводятся
и меняются.

**Что защищает от гонки?** Детерминированный UUID и ограничение БД, а не один
предварительный `SELECT`.

### Отчёт о завершении 8.3

**Что сделано.** Схема книг получила источник, внешний ID, ISBN, cover URL и
время обновления. `BookService` сохраняет внешний результат через атомарный
dialect-aware upsert до возврата вызывающему коду.

**Зачем.** Стабильный внутренний ID теперь сразу пригоден существующим tools и
не зависит от ISBN или повторной доступности Open Library.

**На что обратить внимание.** Local и external записи не склеиваются по
названию. Уникальность защищена БД; SQLite и PostgreSQL используют свои
атомарные `ON CONFLICT` внутри repository.

**Как проверено.** Тесты покрыли повторный поиск, обновление метаданных, два
конкурентных поиска, конфликт внешнего ID, последующее `add_book`, миграцию
существующих данных и новую уникальность.

**Что мы выучили.** Проверка перед insert не заменяет ограничение БД; внешний
ключ и внутренний ключ решают разные задачи.

**Советы на будущее.** Не вводить fuzzy-дедупликацию между поставщиками до
появления подтверждённой продуктовой необходимости.

## 8.4. Timeout, retry, TTL-кэш и fallback

### Результат итерации

Временная недоступность Open Library ограничена коротким ожиданием и одной
повторной попыткой, после чего пользователь получает явно неполный локальный
результат.

### Что реализуем

- Одну повторную попытку GET для timeout/connect error, `429` и `5xx`.
- Отсутствие retry для постоянных `4xx`.
- Ограниченный TTL-кэш успешных результатов по нормализованным `query + limit`.
- Local fallback после исчерпания временных ошибок.
- Различие успешного пустого ответа и отказа зависимости.

### Проверка и критерий готовности

- Тесты покрывают timeout, `429`, `500`, `400`, cache hit, expiry и eviction.
- Успешный пустой ответ не заменяется локальными книгами.
- Ошибка БД не маскируется fallback-механизмом.

### Самоконтроль с ответами

**Когда retry безопасен?** Когда операция не имеет побочного эффекта и ошибка
считается временной.

**Почему пустой ответ не вызывает fallback?** Это валидный результат поиска, а
не признак недоступности.

**Почему fallback помечается явно?** Локальная выборка может быть устаревшей или
неполной.

### Отчёт о завершении 8.4

**Что сделано.** Внешний provider подключён конфигурацией. Resilient catalog
добавляет bounded TTL-кэш, одну повторную попытку временного GET и local
fallback; постоянная ошибка преобразуется в безопасную catalog/tool/API ошибку.

**Зачем.** Чужая сеть больше не определяет неограниченное время ожидания и не
превращает обычный поиск в необработанный traceback.

**На что обратить внимание.** Успешный пустой ответ кэшируется и не вызывает
fallback. `400` не retry-ится; ошибка БД возникает после каталога и этим слоем
не перехватывается.

**Как проверено.** Тесты покрыли timeout, connect failure, успешный retry,
`429`, `500`, `400`, invalid payload, cache hit, expiry, LRU eviction,
некэшируемый fallback, пустой результат, безопасный API/tool error и оба режима
dependency wiring.

**Что мы выучили.** Retry, cache и fallback решают разные проблемы и должны
оставлять наблюдаемый признак фактического пути выполнения.

**Советы на будущее.** Не кэшировать fallback и не увеличивать retry без метрик:
это лишь продлит деградацию и нагрузку на зависимость.

## 8.5. Источник в backend trace и React

### Результат итерации

Пользователь видит в карточке шага Open Library, cache hit или локальный
fallback, при этом raw tool result не попадает в DOM.

### Что реализуем

- Добавим `source`, `degraded`, `cached` в результат `search_books`.
- Выделим безопасные каталожные метаданные в публичном trace DTO.
- Расширим frontend decoder строгим allowlist.
- Покажем источник и предупреждение о неполноте в React trace.

### Проверка и критерий готовности

- Component-тесты покрывают свежий внешний ответ, кэш и fallback.
- Старые run без метаданных продолжают отображаться.
- Неизвестные и вредоносные поля результата отсутствуют в DOM.

### Самоконтроль с ответами

**Почему недостаточно финального текста?** Модель может забыть или неверно
описать фактический источник.

**Почему frontend не читает весь tool result?** Trace является отдельной
границей раскрытия данных.

**Кто определяет деградацию?** Backend по реальному пути выполнения, а не
модель или React.

## 8.6. PostgreSQL и переносимые миграции

### Результат итерации

PostgreSQL с чистой схемой и seed поднимается одной командой, а SQLite остаётся
поддержанным тестовым вариантом.

### Что реализуем

- Добавим Psycopg и Docker Compose с healthcheck и dev-volume.
- Сохраним `DATABASE_URL` единственной точкой выбора СУБД.
- Проверим полную цепочку Alembic и `alembic check` на обеих СУБД.
- Используем SQLite batch-операции там, где обычный `ALTER TABLE` непереносим.

### Проверка и критерий готовности

- `upgrade head`, seed дважды и базовые CRUD/approval-сценарии проходят на
  PostgreSQL.
- Чистая SQLite и обновление существующей SQLite также проходят.
- Импорт старой SQLite в PostgreSQL явно не входит в этап.

### Самоконтроль с ответами

**Почему недостаточно `create_all()`?** Он не проверяет последовательное
обновление реальной схемы по истории миграций.

**Какие различия СУБД опасны?** UUID, JSON, enum/check constraints, timezone и
частичные индексы.

**Почему SQLite остаётся?** Она ускоряет тесты, пока контракт отдельно
доказывается на production-подобной СУБД.

## 8.7. Сквозное закрытие этапа

### Результат итерации

Автоматические сценарии доказывают внешний поиск и fallback от браузера до БД,
а документация позволяет воспроизвести оба режима хранения.

### Что реализуем

- Общий набор доменных contract-тестов для SQLite и PostgreSQL.
- Acceptance: внешний поиск → сохранение → добавление → библиотека → повторный
  поиск без дубликата.
- Acceptance: timeout → retry → local fallback → отметка в UI.
- Отдельный opt-in smoke с реальным Open Library.
- Обновление README, ROADMAP и итогового статуса.

### Проверка и критерий готовности

- Оба сквозных сценария проходят автоматически.
- PostgreSQL разворачивается документированной командой.
- Реальная сеть не требуется основному test suite.
- Учебный отчёт этапа и ответы на самоконтроль сохранены.

### Самоконтроль с ответами

**Что доказывает одинаковый тест на двух СУБД?** Переносимость наблюдаемого
поведения, а не только успешное подключение.

**Почему сетевой smoke отдельный?** Он недетерминирован и зависит от чужой
доступности и лимитов.

**Когда этап завершён?** Когда сквозные сценарии автоматизированы, миграции
воспроизводимы, а отчёт и ответы зафиксированы.

## Критерии готовности всего этапа

- Agent loop и определения tools не импортируют Open Library или
  PostgreSQL-специфичный код.
- Внешний payload не выходит за границу адаптера.
- Возвращаемый внешний `book_id` существует в локальной БД.
- Ошибки каталога безопасны и не раскрывают URL, payload или traceback.
- Источник результата виден пользователю структурированно.
- SQLite и PostgreSQL проходят согласованный набор проверок.
- После каждой итерации существует отдельный коммит и учебный отчёт с
  вопросами и ответами для самоконтроля.
