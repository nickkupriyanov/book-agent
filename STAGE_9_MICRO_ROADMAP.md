# Этап 9: микро-роадмап

Этот документ разбивает этап «Память и RAG» на небольшие проверяемые
итерации. Каждая итерация заканчивается отдельным коммитом, а приложение и
все ранее реализованные сценарии остаются рабочими.

Вернуться к общей карте: [ROADMAP.md](./ROADMAP.md).

## Граница этапа

Целевой пользовательский процесс:

1. пользователь сохраняет заметку о книге;
2. backend разбивает текст на фрагменты с устойчивыми идентификаторами;
3. агент вызывает `search_user_notes` только для вопросов о личных заметках;
4. поиск всегда ограничен текущим пользователем;
5. ответ получает происхождение каждого фрагмента: note ID и book ID;
6. изменение заметки переиндексирует её, а удаление убирает из поиска;
7. текст заметки остаётся недоверенными данными, а не инструкцией агенту;
8. история текущего запуска, структурированные предпочтения и заметки имеют
   разные модели и жизненный цикл.

На этом этапе не добавляем внешний vector database, генерацию embeddings через
сетевой API, общий knowledge graph, автоматический retrieval для каждого
сообщения и долговременную память из всех диалогов. Первый retrieval остаётся
детерминированным и локальным: лексическое ранжирование проверяет архитектурные
границы RAG без нестабильности внешней модели embeddings.

## 9.1. Контракты памяти и схема данных

### Результат итерации

В БД существуют заметки, индексируемые фрагменты и структурированные
предпочтения. Связи, уникальность и каскадное удаление закреплены миграцией.

### Что реализуем

- `UserNote`, связанную с пользователем и необязательной книгой.
- `NoteChunk` с устойчивым ID, позицией и исходным текстом.
- `UserPreference` с уникальным ключом внутри пользователя.
- Миграцию для SQLite и PostgreSQL.
- Проверки чистой миграции и сохранности существующих данных.

### Критерий готовности

- Один пользователь не может получить два preference с одинаковым ключом.
- Удаление заметки каскадно удаляет её chunks.
- Существующие книги, библиотека и agent traces переживают upgrade.

## 9.2. Жизненный цикл заметок и предпочтений

### Результат итерации

Пользователь может создать, прочитать, изменить и удалить свою заметку, а
структурированные предпочтения хранятся отдельно от свободного текста.

### Что реализуем

- Репозитории и сервис памяти с обязательным `user_id` во всех операциях.
- HTTP CRUD для заметок текущего demo-пользователя.
- HTTP read/upsert для структурированных предпочтений.
- Проверки принадлежности книги и заметки пользователю.

### Критерий готовности

- Чужая заметка выглядит как отсутствующая.
- Нельзя привязать заметку к книге вне библиотеки пользователя.
- Изменение и удаление затрагивают ровно одну принадлежащую пользователю
  запись.

## 9.3. Детерминированная индексация и retrieval

### Результат итерации

Текст заметки разбивается на ограниченные фрагменты, а релевантный запрос
возвращает ранжированные совпадения с устойчивым provenance.

### Что реализуем

- Чистый Unicode-aware chunker с перекрытием и предсказуемыми границами.
- Устойчивый chunk ID из note ID, ревизии текста и позиции.
- Лексическое ранжирование по нормализованным токенам.
- Переиндексацию в одной транзакции при create/update.
- Явный пустой результат при отсутствии контекста.

### Критерий готовности

- Одинаковая заметка создаёт одинаковые chunk IDs.
- Изменённый текст не оставляет старых fragments.
- Удалённая заметка не находится.
- Результаты всегда отфильтрованы по `user_id` до ранжирования.

## 9.4. Tool `search_user_notes`

### Результат итерации

Agent loop может явно запросить личные заметки и получает только компактные
цитаты с note ID, book ID и фрагментом.

### Что реализуем

- Строгие Pydantic-схемы аргументов и результата.
- Read-only tool и handler с user scope, зафиксированным dependency wiring.
- Описание tool, объясняющее, когда retrieval нужен и когда не нужен.
- Безопасную сериализацию provenance в trace.

### Критерий готовности

- Лишние поля и неверный limit отклоняются до handler.
- Модель не может передать или подменить `user_id`.
- Обычные библиотечные запросы не вызывают retrieval автоматически.

## 9.5. Политика контекста и граница недоверенных данных

### Результат итерации

Три вида памяти разделены: ограниченная история текущего agent run,
структурированные предпочтения и извлекаемые заметки. Содержимое заметок
помечено как данные и не меняет системные инструкции.

### Что реализуем

- Ограничение истории, отправляемой LLM, без разрыва assistant/tool групп.
- Явные инструкции модели считать note fragments недоверенными цитатами.
- Тест с instruction-like текстом внутри заметки.
- Тест, что библиотечный сценарий не получает содержимое заметок.

### Критерий готовности

- Контекст agent run ограничен документированной политикой.
- Prompt injection остаётся внутри tool result и не попадает в system prompt.
- Preferences не смешиваются с note chunks или историей сообщений.

## 9.6. Сквозная приёмка и закрытие этапа

### Результат итерации

Запрос «Какие темы интересовали меня в последних заметках?» проходит полный
цикл `model -> search_user_notes -> model`, а этап документирован и закрыт.

### Что реализуем

- Acceptance-сценарий с fake LLM и реальной SQLite.
- Негативные сценарии: другой пользователь, нет контекста, удалённая заметка,
  инструкция внутри заметки.
- Проверку полного backend suite и миграций.
- Обновление `ROADMAP.md` и `README.md` с отчётом о завершении.

### Критерий готовности

- Финальный ответ ссылается только на найденные note IDs.
- Нет межпользовательских утечек и выдуманных источников.
- Все критерии этапа 9 из общего roadmap выполнены.
- Основной test suite не выполняет сетевых запросов.
