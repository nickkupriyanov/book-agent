# Этап 5: микро-роадмап

Этот документ разбивает этап «Многошаговые задачи и состояние» на небольшие
проверяемые итерации. Мы проходим их строго по порядку. После каждой итерации
система должна оставаться рабочей, а все тесты — проходить.

Вернуться к общей карте: [ROADMAP.md](./ROADMAP.md).

## Граница этапа

Целевой сценарий:

> Посмотри, что я недавно прочитал, и предложи три похожие книги, которых ещё
> нет в моей библиотеке.

Ожидаемая цепочка:

1. агент получает последние книги со статусом `finished`;
2. агент передаёт их стабильные идентификаторы инструменту рекомендаций;
3. backend находит кандидатов по общим тегам;
4. backend исключает всю текущую библиотеку пользователя и удаляет дубликаты;
5. tool возвращает не более трёх структурированных рекомендаций;
6. модель объясняет результат обычным текстом;
7. acceptance-тест проверяет идентификаторы из tool result, а не стиль текста.

На этом этапе мы не добавляем embeddings, vector database, внешний книжный
каталог, PostgreSQL, frontend и LLM-as-a-judge. Для десяти локальных книг это
скроет учебную механику за ненужной инфраструктурой.

## Рабочий договор для каждой итерации

Каждый микроэтап заканчивается отдельным отчётом:

1. **Что сделано:** изменённые контракты, поток данных и пользовательский
   результат.
2. **На что обратить внимание:** существенные ограничения, компромиссы и
   возможные ошибки.
3. **Как проверено:** конкретные тесты и их результат.
4. **Советы на будущее:** что станет важно на следующих этапах, но не должно
   реализовываться сейчас.
5. **Самоконтроль:** ответы на вопросы из соответствующего раздела своими
   словами, а не пересказ формулировок из документа.

Если критерий готовности не выполнен, микроэтап не считается завершённым.

## 5.1. Метаданные каталога

### Результат итерации

У каждой книги есть небольшой набор нормализованных тегов. Seed повторяемо
создаёт и обновляет эти метаданные. Другого поведения приложения пока не
меняется.

### Что реализуем

- Добавим `Book.tags` как непустой список нормализованных строк в JSON-поле.
- Создадим Alembic-миграцию для существующей базы.
- Дополняем все десять seed-книг тегами так, чтобы:
  - существовало несколько очевидных пересечений;
  - были кандидаты без пересечений;
  - можно было получить меньше трёх результатов;
  - порядок тегов не влиял на результат.
- Сделаем повторный seed обновляющим известные seed-записи, а не создающим
  дубликаты.
- Протянем `tags` в доменную и tool-схемы чтения книги.

Для текущего локального каталога JSON-список проще отдельной many-to-many
модели. Нормализованную таблицу тегов стоит вводить только после появления
поисковых, аналитических или целостностных требований, которые JSON уже не
удовлетворяет.

### На что обратить внимание

- UUID книги остаётся идентичностью; название и набор тегов не являются
  уникальным ключом.
- Теги хранятся в одном регистре, без пробелов по краям и без дублей.
- Миграция должна корректно обработать уже существующие строки.
- Seed обязан синхронизировать метаданные существующих seed-книг. Проверка
  только `book_id not in existing_ids` для этого уже недостаточна.
- Поиск по тегам пока будет выполняться в Python: каталог мал, а этап 8 отдельно
  посвящён реальному каталогу и PostgreSQL.

### Проверка

- Миграция поднимает чистую базу с нуля.
- Миграция обновляет базу предыдущей ревизии без потери библиотеки и трейсов.
- Два запуска seed дают одинаковое состояние.
- У каждой seed-книги есть ожидаемый уникальный набор тегов.
- Полный существующий набор тестов остаётся зелёным.

### Критерий готовности

Теги доступны через API/tools, повторный seed не меняет количество книг, а
чистая и обновлённая базы имеют одинаковую схему.

### Самоконтроль

**Почему нельзя использовать название книги для дедупликации?**

Название не является стабильной идентичностью: существуют переиздания,
переводы, одинаковые названия и варианты написания. Дедупликация по названию
может как ошибочно объединить разные книги, так и оставить два представления
одной записи. Внутренний `book_id` задаёт однозначную идентичность.

**Почему JSON со списком тегов приемлем сейчас, но не обязательно навсегда?**

Сейчас каталог детерминированный и состоит из десяти записей: нам важнее
прозрачно изучить планирование агента, чем оптимизировать запросы. При внешнем
каталоге могут понадобиться индексы, словарь тегов, синонимы, веса и сложные
запросы. Тогда отдельная модель или специализированный поиск будут оправданы
измеряемой потребностью.

**Что должен означать повторный seed: «ничего не делать» или
«восстановить эталон»?**

Для принадлежащих приложению seed-записей он должен восстановить эталонные
метаданные по стабильному ID. Иначе изменение формата seed не попадёт в уже
созданную dev-базу. При этом seed не должен удалять пользовательские записи или
неизвестные книги.

### Совет на будущее

Не добавлять веса, иерархии и embeddings к тегам заранее. Сначала соберём
детерминированный baseline; позже его качество можно будет сравнить с более
сложным подходом.

### Итог итерации — завершена 27 июля 2026

- В `Book` добавлен обязательный JSON-массив `tags` с безопасным пустым
  значением для строк, существовавших до миграции.
- Миграция `20260727_03` добавляет поле без потери книг, библиотеки и agent
  traces.
- Все десять seed-книг получили нормализованные, отсортированные и уникальные
  теги.
- Seed теперь синхронизирует название, автора и теги известных книг по
  стабильному UUID; неизвестные записи не удаляет.
- Теги доступны в HTTP `BookResponse` и общем `BookToolResult`.
- Проверено обновление базы с `20260720_02`: существующая «Дюна» сохранила
  статус `finished` и получила эталонные теги.
- `alembic check` не обнаружил расхождений; все 110 тестов проходят без сети.

## 5.2. Детерминированный подбор кандидатов

### Результат итерации

Доменный сервис без LLM умеет по списку исходных книг вернуть ранжированных
кандидатов, которых нет в библиотеке пользователя.

### Что реализуем

- Введём небольшой тип результата рекомендации:
  `book`, `matched_tags`, `score`.
- Источниками будут стабильные `source_book_ids`.
- Кандидат получает один балл за каждый общий уникальный тег с исходными
  книгами.
- Книги с нулевым пересечением исключаются.
- Из кандидатов исключаются:
  - исходные книги;
  - все книги, уже находящиеся в библиотеке пользователя, независимо от статуса.
- Результат дедуплицируется по `book_id`.
- Порядок будет детерминированным:
  `score DESC`, затем `book_id ASC`.
- `limit` применяется после фильтрации, дедупликации и сортировки.

Алгоритм остаётся обычной доменной логикой. Модель выбирает, когда вызвать tool,
но не решает, можно ли рекомендовать уже добавленную книгу.

### На что обратить внимание

- Нельзя доверять модели список исключений: она может забыть часть библиотеки.
- `matched_tags` нужны не только для текста модели, но и для объяснимости теста.
- Детерминированный tie-break обязателен для воспроизводимых сценариев.
- Неизвестный source ID должен давать контролируемую ошибку, а не молча менять
  смысл рекомендации.
- Пустой результат является корректным бизнес-результатом.

### Проверка

- Более похожая книга ранжируется выше менее похожей.
- Равные оценки дают стабильный порядок.
- Одна книга не появляется дважды даже при совпадении с несколькими источниками.
- Любой статус в библиотеке исключает книгу из кандидатов.
- При недостатке совпадений возвращается меньше запрошенного лимита.
- Неизвестный source ID не приводит к выдуманным рекомендациям.

### Критерий готовности

Рекомендатор полностью тестируется через `BookService` и repository без agent
loop, LLM и HTTP.

### Самоконтроль

**Почему фильтрация уже добавленных книг должна быть на backend, если модель
перед этим получила библиотеку?**

История модели — контекст для планирования, а не граница целостности. Модель
может пропустить запись, сократить контекст или сформировать неверные аргументы.
Backend знает пользователя и может гарантировать инвариант для каждого вызова.

**Почему лимит применяется в самом конце?**

Если ограничить каталог до фильтрации, первые записи могут оказаться
дубликатами или уже находиться в библиотеке. После их удаления останется меньше
результатов, хотя допустимые кандидаты существовали. Лимит относится к
валидному итоговому набору.

**Чем детерминированный tie-break полезен помимо удобства тестов?**

Он делает повторный запрос воспроизводимым, упрощает анализ трасс и не позволяет
случайному порядку БД менять пользовательский результат. Это снижает шум при
будущем сравнении prompt-ов и алгоритмов.

### Совет на будущее

Сохранять этот алгоритм как baseline. Когда появится RAG или внешний каталог,
новый подход должен доказывать преимущество на eval-наборе, а не просто казаться
умнее.

### Итог итерации — завершена 30 июля 2026

- Добавлен доменный `RecommendationCandidate` с книгой, совпавшими тегами и
  числовой оценкой.
- `BookService.find_similar_books` принимает пользователя, исходные `book_id`
  и лимит без зависимости от LLM, HTTP или tool registry.
- Оценка равна числу уникальных общих тегов со всеми исходными книгами.
- Исходные книги и вся библиотека пользователя исключаются внутри backend
  независимо от читательского статуса.
- Результаты без общих тегов удаляются, остальные дедуплицируются по UUID и
  сортируются по `score DESC`, затем `book_id ASC`.
- Лимит применяется только после фильтрации, дедупликации и сортировки.
- Пустой набор кандидатов является корректным результатом; неизвестный source
  ID даёт существующую доменную `BookNotFoundError`.
- Добавлено семь доменных сценариев; все 117 тестов проходят без сети.

## 5.3. Строгий read-tool рекомендаций

### Результат итерации

Registry публикует и безопасно исполняет новый read-tool
`find_similar_books`. Его результат содержит достаточно данных, чтобы модель
объяснила каждую рекомендацию без догадок.

### Что реализуем

- Аргументы:
  - `source_book_ids`: непустой список уникальных UUID;
  - `limit`: по умолчанию `3`, с небольшим верхним пределом.
- Результат:
  - `recommendations`;
  - для каждой рекомендации — `book`, `matched_tags`, `score`.
- Handler получает текущего пользователя из dependency wiring, а не из
  аргументов модели.
- Доменная ошибка неизвестного источника преобразуется в безопасный
  `ToolResult.error`.
- Tool регистрируется в существующем allowlist.
- Описание инструмента явно сообщает, что библиотека пользователя исключается
  автоматически.

### На что обратить внимание

- `user_id` нельзя включать в доступную модели схему.
- Pydantic должен запрещать дополнительные поля.
- Tool-обёртка только валидирует, адаптирует ошибку и вызывает сервис; алгоритм
  ранжирования в ней не дублируется.
- Пустой список рекомендаций — успешный output, а не техническая ошибка.
- Структурированный tool result становится проверяемым источником истины;
  финальный текст модели остаётся презентацией.

### Проверка

- JSON Schema соответствует Pydantic-модели.
- Пустой `source_book_ids`, дубликаты, лишние поля и неверный `limit`
  отклоняются до handler.
- Registry исполняет tool только под зарегистрированным именем.
- Контрактный тест проверяет полный сериализованный результат.
- Доменная ошибка безопасно нормализуется.

### Критерий готовности

Tool можно вызвать напрямую через registry, получить стабильные рекомендации и
доказать, что он не раскрывает и не принимает чужой `user_id`.

### Самоконтроль

**Почему `user_id` — dependency handler-а, а не аргумент tool call?**

Идентичность пользователя приходит из доверенной границы приложения. Если
модель может передать `user_id`, она получает возможность запросить чужие
данные. Схема инструмента должна содержать только параметры задачи, но не
авторизационный контекст.

**Почему пустой результат не следует кодировать как ошибку?**

«Подходящих книг нет» — валидное состояние каталога. Ошибка означает, что
операция не могла корректно выполниться. Такое различие позволяет модели честно
ответить пользователю и не пытаться бесконечно исправлять корректный запрос.

**Какая часть описания tool является частью безопасности, а не только UX для
модели?**

Явное обещание автоматического исключения библиотеки отражает реальную
backend-гарантию и не предлагает модели передавать чувствительный или
ненадёжный список исключений. Однако само описание не является защитой:
инвариант всё равно обязан исполнять handler/service.

### Совет на будущее

При смене LLM-провайдера сохранять общий Pydantic-контракт. Особенности формата
конкретного API должны оставаться внутри LLM-адаптера.

### Итог итерации — завершена 3 августа 2026

- Добавлен read-tool `find_similar_books` с отдельными строгими Pydantic-схемами
  аргументов, рекомендации и полного результата.
- `source_book_ids` требует непустой список уникальных UUID; `limit` по
  умолчанию равен трём и ограничен диапазоном от 1 до 10.
- `user_id` отсутствует в публичной JSON Schema и подставляется handler-ом из
  доверенного dependency wiring.
- Handler не содержит алгоритм рекомендаций: он вызывает
  `BookService.find_similar_books` и преобразует доменный результат в tool DTO.
- Неизвестная исходная книга нормализуется в безопасный
  `ToolErrorCode.BOOK_NOT_FOUND`; пустой список рекомендаций остаётся успешным
  output.
- Описание tool сообщает модели, что текущая библиотека исключается backend-ом
  автоматически; реальная гарантия остаётся в доменном сервисе.
- Tool зарегистрирован в общем allowlist и передаётся agent loop вместе с
  четырьмя существующими инструментами.
- Контракт, validation-before-handler, полная сериализация результата и
  dependency wiring покрыты тестами; все 125 тестов проходят без сети.

## 5.4. Последние прочитанные книги

### Результат итерации

Существующий `get_user_library` может явно запросить последние завершённые
книги в ограниченном количестве. Понятие «последние» имеет одно
детерминированное значение.

### Что реализуем

- Расширим аргументы read-tool необязательными `limit` и
  `recent_first`.
- При `recent_first=true` repository сортирует по
  `updated_at DESC`, затем `book_id ASC`.
- Ограничение выполняется запросом repository после всех фильтров.
- Старое поведение без новых аргументов сохраняется.
- Обновим описание tool, чтобы модель знала рекомендуемую форму запроса для
  сценария: `status=finished`, `recent_first=true`, ограниченный `limit`.

### На что обратить внимание

- «Последняя» книга определяется временем изменения статуса, а не временем
  добавления в библиотеку.
- Равные timestamps требуют стабильного tie-break.
- Нельзя менять порядок старых вызовов неявно: это сломает существующий
  контракт.
- На SQLite тестовые timestamps лучше задавать явно, иначе быстрые операции
  могут иметь одинаковое время.

### Проверка

- Без новых аргументов сохраняется прежний результат.
- Фильтр применяется до лимита.
- Недавно завершённая книга стоит первой.
- Равные timestamps сортируются стабильно.
- Tool schema отклоняет нулевой, отрицательный и слишком большой limit.

### Критерий готовности

Scripted fake может однозначно запросить последние `finished`-книги и передать
полученные ID следующему tool.

### Самоконтроль

**Почему `created_at` не отвечает на вопрос «что я недавно прочитал»?**

Книга могла год находиться в `want_to_read` и быть завершена сегодня.
`created_at` покажет момент добавления, а не последнее изменение читательского
состояния. Для текущей модели данных ближайшая корректная семантика —
`updated_at`.

**Почему сортировку нельзя оставить модели после получения всей библиотеки?**

Это тратит контекст, увеличивает шанс ошибки и делает значение «последние»
зависимым от модели. Сортировка и лимит — детерминированная работа с данными,
которую надёжнее и дешевле выполнить в repository.

**В какой момент `updated_at` перестанет быть достаточным?**

Когда потребуется история повторных прочтений, отдельные даты начала и
завершения или аудит переходов. Тогда нужна модель событий/сессий чтения.
Добавлять её сейчас без такого сценария преждевременно.

### Совет на будущее

Не превращать `get_user_library` в универсальный язык запросов. Если появится
второй существенно иной сценарий сортировки, лучше ввести явный доменный
запрос, чем наращивать набор произвольных параметров.

### Итог итерации — завершена 3 августа 2026

- `get_user_library` получил необязательные аргументы `recent_first` и `limit`;
  старые вызовы без них сохраняют прежнее поведение.
- `limit` допускает значения от 1 до 50 или `null`; `recent_first` по умолчанию
  равен `false`, дополнительные поля по-прежнему запрещены.
- При `recent_first=true` repository сортирует по `updated_at DESC`, затем по
  стабильному `book_id ASC`.
- Фильтр по читательскому статусу применяется до сортировки и SQL `LIMIT`,
  поэтому более новая книга другого статуса не вытесняет завершённые книги.
- Описание tool явно подсказывает модели форму запроса для сценария:
  `status=finished`, `recent_first=true`, ограниченный `limit`.
- Тестовые timestamps задаются явно: проверены сохранение старого порядка,
  фильтрация до лимита, recent order и tie-break при равном времени.
- Все 128 тестов проходят без сети.

## 5.5. Рабочее состояние запуска

### Результат итерации

Backend отдельно хранит историю разговора и компактное рабочее состояние:
цель, успешно завершённые действия, исходный и оставшийся бюджет шагов.

### Что реализуем

- Введём строгую Pydantic-модель `AgentWorkingState`.
- Состояние включает:
  - `goal` — исходную пользовательскую цель;
  - `completed_actions` — краткие записи об успешных tool calls;
  - `initial_step_budget`;
  - `remaining_step_budget`.
- Состояние сохраняется в `AgentRun` как JSON фиксированной схемы и отдаётся в
  HTTP response.
- После каждого модельного шага backend пересчитывает оставшийся бюджет.
- В `completed_actions` попадают только фактически завершённые вызовы; ошибка
  tool не выдаётся за выполненное действие.
- Полные аргументы и outputs остаются в `AgentStep`; state хранит ссылки и
  краткие итоги, не копируя весь trace.
- Компактный снимок state передаётся модели, чтобы ей был виден оставшийся
  бюджет, но политики остановки всё равно исполняет backend.

### На что обратить внимание

- История отвечает «что было сказано», state — «чего достигаем и что уже
  подтверждённо сделано».
- JSON-state не должен стать неструктурированной корзиной для любых данных.
- `remaining_step_budget` вычисляет backend; модель не может его увеличить.
- Ошибочный, отклонённый или остановленный повтором tool call не является
  completed action.
- Миграция должна создать валидное начальное состояние для старых runs.

### Проверка

- Новый run стартует с правильной целью и полным бюджетом.
- Бюджет уменьшается ровно на один на каждый вызов модели.
- Успешные tool calls появляются в правильном порядке.
- Ошибочный tool result не помечается успешным действием.
- State сохраняется и восстанавливается новой SQLAlchemy-сессией.
- Старые API-поля и trace продолжают работать.

### Критерий готовности

По одному `AgentRun` без интерпретации текста модели можно определить цель,
успешно выполненные действия и оставшийся бюджет.

### Самоконтроль

**Почему `completed_actions` нельзя восстанавливать только из assistant
messages?**

Assistant message выражает намерение модели вызвать инструмент, но не
доказывает исполнение. Вызов мог не пройти валидацию, вернуть доменную ошибку
или быть остановлен политикой. Завершённое действие определяется результатом
backend execution.

**Зачем хранить state, если подробный trace уже содержит все данные?**

Trace оптимизирован для аудита и воспроизведения, но требует интерпретации
множества событий. State — компактная текущая проекция, которой пользуются
политики и будущий resume. При этом trace остаётся источником доказательств,
почему state принял такое значение.

**Почему бюджет принадлежит backend, хотя модель планирует шаги?**

Бюджет — ограничение ресурсов и безопасности. Если модель могла бы менять его,
лимит перестал бы быть гарантией завершения. Модель может адаптировать план к
оставшемуся бюджету, но не управлять самим ограничением.

### Совет на будущее

На этапе 6 это состояние станет основой паузы и возобновления. Не добавлять
сейчас pending approval или optimistic locking: их инварианты появятся только в
следующем сценарии.

## 5.6. Идемпотентность write-tools

### Результат итерации

Безопасный повтор уже успешно выполненного `add_book` не создаёт вторую запись
и возвращает структурированный успешный no-op. Конфликтующее повторение не
скрывается.

### Что реализуем

- Оставим строгую HTTP/доменную операцию `add_book` без изменения:
  обычный дубликат по-прежнему даёт `409`.
- Для агентного tool определим отдельную retry-семантику:
  - книга уже есть с тем же статусом → success, `changed=false`;
  - книги ещё нет → success, `changed=true`;
  - книга есть с другим статусом → контролируемый conflict; tool не меняет её
    неявно.
- Добавим к результату tool явный признак `changed`.
- Сохраним текущую защиту одного run от точного последовательного повтора:
  идемпотентность защищает повторную доставку между runs, а детектор повтора —
  от бессмысленного цикла внутри run.

### На что обратить внимание

- «Идемпотентно» не означает «любая ошибка превращается в success».
- Повтор не должен обновлять `updated_at`, если состояние не изменилось.
- Нельзя автоматически менять существующий статус через `add_book`; для этого
  есть отдельный `update_book_status`.
- Уникальное ограничение БД остаётся последней защитой от дублей.
- Проверка существования и insert могут столкнуться при конкуренции. Полную
  конкурентную идемпотентность с ключами запросов рассматриваем на этапе 6.

### Проверка

- Два одинаковых вызова tool создают одну строку.
- Второй результат имеет `changed=false`.
- Повтор не меняет timestamp записи.
- Другой статус возвращает conflict и сохраняет исходное состояние.
- HTTP endpoint продолжает возвращать `409` для дубликата.
- Внутренний repeated-call guard agent loop продолжает работать.

### Критерий готовности

Повторная доставка безопасного write-tool наблюдаемо не меняет БД второй раз и
не ломает старый HTTP-контракт.

### Самоконтроль

**Почему идемпотентность лучше выражать через `changed`, а не одинаковый
текстовый ответ?**

Текст нельзя надёжно использовать в логике и acceptance-тестах. Структурированный
флаг различает реальное изменение и успешный повтор, оставаясь независимым от
формулировки модели.

**Почему повтор с другим статусом — конфликт, а не безопасное обновление?**

Это уже другое намерение и другой доменный переход. Неявное обновление смешало
бы два инструмента, расширило полномочия `add_book` и могло затереть актуальное
состояние при повторе старого сообщения.

**Чем защита от повторного tool call отличается от идемпотентности?**

Детектор предотвращает цикл и экономит шаги внутри одного запуска.
Идемпотентность гарантирует безопасный эффект, если одинаковая команда всё же
доставлена повторно — например, в новом HTTP-запросе после сетевого сбоя. Нужны
обе защиты, потому что они работают на разных уровнях.

### Совет на будущее

Для необратимых или конкурентных действий одного сравнения текущего состояния
недостаточно. На этапе 6 появятся idempotency key, сохранённое pending action и
контроль версии.

## 5.7. Многошаговый сценарий и acceptance-тест

### Результат итерации

`POST /api/agent/runs` выполняет полный сценарий рекомендации через scripted
fake:

`get_user_library` → `find_similar_books` → финальный ответ.

Тест доказывает качество результата структурированными инвариантами.

### Что реализуем

- Уточним system prompt только в пределах доступных возможностей:
  - использовать недавние `finished`-книги как источники;
  - не выдумывать книги и ID;
  - объяснять рекомендации через `matched_tags`;
  - честно возвращать меньше трёх вариантов.
- Подготовим scripted fake с коррелированными `tool_call_id`.
- Добавим helper для извлечения структурированного результата
  `find_similar_books` из trace в acceptance-тесте.
- Проверим сценарий при наличии трёх кандидатов.
- Проверим повтор после добавления одного кандидата в библиотеку.
- Проверим сценарий, где допустимых кандидатов меньше трёх.
- Убедимся, что все четыре MVP-сценария доступны через backend API.

### Инварианты acceptance-теста

- run завершён со статусом `completed`;
- использованы только разрешённые tools;
- сначала получена библиотека, затем выполнен подбор;
- все recommendation IDs существуют в каталоге;
- IDs уникальны;
- ни один ID не находится в библиотеке пользователя;
- каждый результат имеет ненулевой `score` и непустые `matched_tags`;
- количество результатов не превышает запрошенный limit;
- при недостатке данных backend не дополняет результат выдуманными IDs;
- trace и working state согласованы;
- финальный ответ существует, но его точная формулировка не сравнивается.

### На что обратить внимание

- Scripted fake проверяет orchestration, а не интеллект реальной модели.
- Нельзя утверждать, что конкретный русский текст всегда будет одинаковым.
- Проверка только финального ответа пропустит выдуманные ID и нарушения
  фильтрации.
- Проверка только последовательности tools пропустит неверный бизнес-результат.
- Количество шагов и tool calls следует зафиксировать как наблюдаемую стоимость,
  но не оптимизировать без baseline.

### Проверка

- Новый scenario/acceptance-набор проходит без сети.
- Все тесты этапов 1–4 остаются зелёными.
- Миграции доходят до head; `alembic check` не видит расхождений.
- Отдельный ручной smoke с реальным провайдером документирован, но не входит в
  обязательный unit/acceptance запуск.
- README и основной roadmap отражают завершённый backend MVP.

### Критерий готовности

Все критерии этапа 5 из `ROADMAP.md` выполнены, итог рекомендации доказан
структурированными данными, а полный тестовый набор не требует сети.

### Самоконтроль

**Почему scripted fake не доказывает, что реальная модель всегда выберет
правильный план?**

Fake воспроизводит заранее заданные ответы и доказывает корректность backend
loop, tool contracts, состояния и бизнес-инвариантов. Способность реальной
модели устойчиво выбрать такой план — отдельное вероятностное свойство, которое
позже измеряется eval-набором.

**Почему нельзя оценивать рекомендацию сравнением полного финального текста?**

Несколько формулировок могут одинаково корректно объяснять те же книги, а
красивый текст может содержать неверные или уже добавленные книги. Проверять
нужно стабильные ID и доменные ограничения; текст достаточно проверить на
наличие и связь с подтверждёнными данными в отдельном eval.

**Как понять, что модель вызвала лишний инструмент?**

Сначала задаётся минимальная необходимая цепочка для сценария. Затем trace
сравнивается с ней: вызов, который не добавил новых данных, не изменил состояние
и не был нужен для исправления контролируемой ошибки, является кандидатом на
лишний. Решение принимается по данным trace, а не по длине ответа.

**Почему тест должен проверять и trace, и итоговое состояние каталога/библиотеки?**

Trace показывает путь и полномочия, но сохранённый trace сам по себе не
гарантирует реальный эффект или отсутствие побочного эффекта. Состояние БД
показывает результат, но не объясняет, как он был достигнут. Вместе они
проверяют и процесс, и бизнес-итог.

### Совет на будущее

Сохранить сценарии этого этапа как первые записи будущего eval dataset. На
этапе 10 к ним можно добавить несколько вариантов формулировок, реальные
модельные прогоны, стоимость, latency и долю соблюдённых инвариантов.
