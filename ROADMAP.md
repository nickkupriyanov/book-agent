# Roadmap: учебный AI-агент для книг

Этот роадмап — последовательность проверяемых учебных этапов, а не календарный план. Каждый этап добавляет одну новую идею к уже работающей системе.

Вернуться к обзору проекта: [README.md](./README.md).

## Правила прохождения

- Не переходить к следующему этапу, пока не выполнены все критерии готовности текущего.
- На каждом этапе создавать наблюдаемый вертикальный сценарий: вход → выполнение → проверяемый результат.
- Проверять бизнес-результат по состоянию приложения, а не только по тексту модели.
- Добавлять минимум один негативный тест: неверный ввод, запрещённое действие, ошибка зависимости или повторный запрос.
- Для детерминированных тестов использовать fake-провайдер; реальные LLM-вызовы держать в отдельном integration/eval-наборе.
- После этапа делать небольшой отдельный commit и уметь объяснить поток данных своими словами.
- Не добавлять абстракцию «на будущее», пока не появился второй реальный вариант, который подтверждает её необходимость.

## Этап 1. Обычный backend без LLM

### Наблюдаемый результат

Через HTTP API можно создать библиотеку из локального каталога, получить книги по статусу, добавить книгу и изменить её статус. Все операции работают без модели и сети.

### Цель

Построить проверяемую доменную основу и увидеть границу между обычной бизнес-логикой и будущим агентом.

### Что понять

- роли API, доменного сервиса и repository;
- разницу между доменной моделью и HTTP DTO;
- ограничения и уникальность на уровне базы данных;
- назначение миграций;
- почему LLM не должна заменять детерминированную бизнес-логику.

### Что реализовать

- Инициализировать `backend/` с FastAPI, Pydantic, SQLAlchemy, Alembic и pytest.
- Описать `Book` и `LibraryEntry`.
- Использовать статусы `want_to_read`, `reading`, `finished`.
- Запретить повторное добавление одной книги одному пользователю.
- Подготовить небольшой локальный seed-каталог с известными идентификаторами.
- Реализовать repository и доменный `BookService`.
- Добавить CRUD endpoints для поиска, просмотра библиотеки, добавления и смены статуса.
- Поднять SQLite через конфигурацию `DATABASE_URL`.

### Практические упражнения

1. Добавить «Дюну» в `want_to_read` и получить её через фильтр библиотеки.
2. Перевести книгу из `reading` в `finished`.
3. Объяснить, какие проверки должны находиться в сервисе, а какие — в БД.

### Тесты

- Unit: поиск по названию нечувствителен к регистру.
- Unit: допустимый переход статуса сохраняется.
- API: добавленная книга появляется в библиотеке.
- Integration: данные сохраняются между запросами в тестовой SQLite.
- **Негативный:** повторное добавление возвращает доменную ошибку/`409`, а не создаёт дубликат.
- **Негативный:** неизвестный `book_id` не изменяет БД.

### Критерии готовности

- Все операции выполняются без LLM и внешней сети.
- Доменный сервис не зависит от FastAPI.
- Миграция создаёт базу с нуля.
- Повторный запуск seed не создаёт дубликаты.
- Тесты проходят в одной документированной команде.

### Вопросы для самопроверки

- Почему нельзя дать модели инструмент `execute_sql(query)`?
- Где гарантируется уникальность книги в библиотеке?
- Чем HTTP-схема отличается от таблицы SQLAlchemy?
- Как протестировать сервис без запуска сервера?

**Мои заметки — этап завершён 13 июля 2026:**

- Модели не выдаётся `execute_sql`, потому что такой интерфейс обходит allowlist, доменные правила и контроль аргументов. Будущие tools будут вызывать только ограниченные методы `BookService`.
- Уникальность книги гарантируется составным первичным ключом
  `(user_id, book_id)` в БД; сервис заранее преобразует обычный повтор в
  понятную доменную ошибку.
- HTTP-схема описывает внешний контракт и валидацию запроса, а SQLAlchemy-модель — хранение, связи и ограничения. Они могут изменяться независимо.
- `BookService` тестируется напрямую через repository и временную SQLite без запуска Uvicorn; API отдельно проверяется через dependency override.
- SQLite `lower()` не обеспечил регистронезависимый поиск по кириллице. Для маленького локального seed-каталога поиск выполняется через Unicode `casefold()` в Python; внешний поиск позже будет скрыт за `BookCatalog`.
- Проверка: 12 тестов проходят; миграция поднимает чистую SQLite; два запуска seed дают `added=10`, затем `added=0` при неизменном `total=10`.

## Этап 2. Один LLM-вызов без инструментов

### Наблюдаемый результат

Endpoint принимает сообщение и возвращает один текстовый ответ через реальный LLM-адаптер. Тот же endpoint тестируется без сети через fake-провайдер.

### Цель

Научиться изолировать внешний AI API и его нестабильные детали от приложения до появления agent loop.

### Что понять

- dependency inversion и adapter pattern;
- system instructions, user message и model response;
- таймауты, retry и различие временной/постоянной ошибки;
- конфигурацию через environment variables;
- почему unit-тесты не должны зависеть от реальной модели.

### Что реализовать

- Ввести минимальный контракт `LLMProvider.generate(messages, tools) -> ModelResponse`.
- На этом этапе передавать пустой список `tools`.
- Реализовать адаптер одного провайдера; OpenAI Responses API — рекомендуемый первый вариант.
- Нормализовать текст, usage и идентификатор ответа в `ModelResponse`.
- Реализовать `FakeLLMProvider` с заранее заданной очередью ответов.
- Добавить настройки API key, model, timeout и provider через `.env.example`.
- Не логировать API key и полное содержимое секретных заголовков.

### Практические упражнения

1. Попросить модель кратко описать книгу из пользовательского сообщения.
2. Заменить реальный адаптер fake-реализацией без изменения endpoint.
3. Искусственно вызвать timeout и проследить путь ошибки до HTTP-ответа.

### Тесты

- Unit: fake-провайдер получает ожидаемые сообщения.
- Unit: сырой ответ реального адаптера преобразуется в общий `ModelResponse`.
- API: endpoint работает с dependency override.
- **Негативный:** timeout преобразуется в контролируемую ошибку, а не необработанный traceback.
- **Негативный:** отсутствие API key обнаруживается при создании реального адаптера, но не мешает unit-тестам с fake.

### Критерии готовности

- Доменный слой не импортирует SDK провайдера.
- Unit/API-тесты не выполняют сетевые запросы.
- Реальный smoke test запускается отдельно и требует явного API key.
- Ошибки провайдера имеют внутреннюю нормализованную форму.

### Вопросы для самопроверки

- Какие данные адаптер должен сохранить, а какие скрыть?
- Почему общий интерфейс не должен копировать все параметры первого SDK?
- Где заканчивается ответственность retry?
- Чем fake отличается от mock одного метода SDK?

## Этап 3. Инструменты и строгие контракты

### Наблюдаемый результат

Приложение публикует четыре определения инструментов и может безопасно выполнить каждый из них напрямую, без решения модели.

### Цель

Сделать инструменты маленьким, валидируемым и тестируемым API между моделью и приложением.

### Что понять

- function/tool calling как запрос модели к приложению, а не исполнение внутри модели;
- JSON Schema и Pydantic validation;
- allowlist инструментов;
- различие технической и доменной ошибки;
- принцип минимальных полномочий.

### Что реализовать

- `ToolDefinition`, `ToolCall`, `ToolResult` и структурированный `ToolError`.
- Registry с явной регистрацией разрешённых инструментов.
- `search_books(query, limit)`.
- `get_user_library(status?)`.
- `add_book(book_id, status)`.
- `update_book_status(book_id, status)`.
- Отдельные Pydantic-схемы аргументов и результатов каждого инструмента.
- Адаптацию общих tool definitions в формат конкретного LLM API внутри LLM-адаптера.
- Классификацию инструментов как `read` или `write`; `destructive` появится позднее.

### Практические упражнения

1. Выполнить каждый tool напрямую через registry.
2. Передать лишнее поле и неверный статус.
3. Сравнить доменный метод сервиса и тонкую tool-обёртку.

### Тесты

- Unit: schema принимает корректные и отклоняет лишние/неверные поля.
- Unit: registry вызывает только зарегистрированный handler.
- Unit: доменная ошибка преобразуется в безопасный `ToolResult`.
- Contract: tool definition, которую видит модель, соответствует Pydantic-схеме.
- **Негативный:** неизвестное имя инструмента не приводит к динамическому импорту или выполнению кода.
- **Негативный:** произвольный SQL и дополнительные аргументы отклоняются.

### Критерии готовности

- У каждого tool есть имя, ясное описание, строгий input и структурированный output.
- Модель не может вызвать service/repository иначе чем через registry.
- Tool-обёртки не дублируют доменную логику.
- Все инструменты тестируются без LLM.

### Вопросы для самопроверки

- Почему описание инструмента является частью его интерфейса?
- Где валидируются аргументы до побочного эффекта?
- Какие ошибки полезно вернуть модели, а какие следует скрыть?
- Чем tool отличается от обычного Python-метода?

## Этап 4. Самописный agent loop

### Наблюдаемый результат

Запрос «Найди “Дюну” и добавь в список на чтение» приводит к последовательности `search_books` → `add_book` → финальный ответ. Backend управляет каждым шагом и сохраняет трейс.

### Цель

Самостоятельно реализовать фундаментальную механику агента без фреймворка.

### Что понять

- цикл model → tool call → validation → execution → tool result → model;
- историю сообщений и корреляцию `tool_call_id`;
- условия завершения;
- лимит шагов и защита от циклов;
- различие ошибки инструмента и падения всего запуска.

### Что реализовать

- `AgentRun` и `AgentStep` с уникальными идентификаторами.
- Статусы `running`, `completed`, `failed`, `step_limit_exceeded`.
- Синхронный agent loop с небольшим настраиваемым `max_steps`.
- Обработку одного и нескольких tool calls в ответе согласно возможностям выбранного провайдера.
- Валидацию до вызова handler.
- Передачу `ToolResult` обратно модели с корректной корреляцией.
- Детектор точного повторения одинакового tool call без изменения состояния.
- Сохранение причины остановки.
- Синхронный HTTP endpoint запуска; streaming пока не добавлять.

### Практические упражнения

1. Выполнить запрос, требующий двух tools подряд.
2. Настроить fake-провайдер, который трижды повторяет один вызов.
3. Вернуть ошибку инструмента и позволить модели один раз скорректировать аргументы.

### Тесты

- Unit: scripted fake проходит цепочку из двух tools и финального ответа.
- Unit: каждый `ToolResult` связан с исходным `tool_call_id`.
- Unit: loop останавливается на финальном ответе.
- Integration: добавление книги действительно меняет БД ровно один раз.
- **Негативный:** бесконечная последовательность достигает `step_limit_exceeded`.
- **Негативный:** повтор одинакового вызова обнаруживается раньше бесконечного цикла.
- **Негативный:** неизвестный tool создаёт контролируемый error result.

### Критерии готовности

- Ни один tool не выполняется без registry и validation.
- Любой запуск имеет конечное состояние и причину остановки.
- Цепочка полностью воспроизводится с fake-провайдером.
- Ошибка одного шага видна в трейсе.
- В коде нет LangChain, LangGraph, CrewAI или Agents SDK.

### Вопросы для самопроверки

- Кто решает, что запуск завершён?
- Что считается одним шагом?
- Почему лимит шагов нужен даже хорошей модели?
- Когда ошибка инструмента должна вернуться модели, а когда завершить запуск?

**Мои заметки — этап завершён 23 июля 2026:**

- Один `AgentStep` — одно обращение к модели и все tool calls из её ответа. Результаты всех вызовов возвращаются модели перед следующим шагом.
- Backend завершает запуск по собственным правилам: ответ без tool calls даёт `completed`; исчерпание `AGENT_MAX_STEPS` — `step_limit_exceeded`; точный последовательный повтор вызовов — `failed` с причиной `repeated_tool_call`.
- Сигнатура повтора учитывает имя tool и канонические аргументы, но игнорирует новый `tool_call_id`. Повтор не выполняется второй раз.
- Контролируемый `ToolResult.error` возвращается модели, поэтому она может исправить аргументы. Ошибка провайдера или неожиданный баг завершают run, сохраняются в трейсе и пробрасываются до HTTP-слоя.
- `tool_call_id` связывает каждый запрос модели с конкретным результатом, в том числе при нескольких вызовах в одном ответе.
- `AgentRun` и `AgentStep` сохраняются в SQLite. `POST /api/agent/runs` синхронно возвращает финальный статус, ответ, причину остановки и упорядоченный трейс.
- Весь сценарий воспроизводится через scripted fake без сети: `search_books` → `add_book` → финальный ответ; состояние библиотеки меняется ровно один раз.
- Проверка: 108 тестов проходят; чистая SQLite поднимается миграциями до `20260720_02`; `alembic check` не обнаруживает расхождений.

**Ответы для самопроверки:**

- Запуск завершает backend, а не модель: модель возвращает ответ, backend интерпретирует его и применяет политики остановки.
- Лимит шагов нужен, потому что даже корректно работающая модель может зациклиться, повторять действия или не сформировать финальный ответ.
- Ожидаемая ошибка аргументов или домена возвращается модели как `ToolResult.error`; ошибка провайдера и неожиданный сбой приложения завершают весь запуск.

## Этап 5. Многошаговые задачи и состояние

Подробный порядок реализации: [микро-роадмап этапа 5](./STAGE_5_MICRO_ROADMAP.md).
Он делит этап на семь проверяемых итераций, для каждой фиксирует границы,
тесты, критерий готовности, советы и вопросы самоконтроля с ответами.

### Наблюдаемый результат

Запрос рекомендации анализирует завершённые книги, получает кандидатов, исключает уже добавленные и возвращает три объяснённых варианта. Тест проверяет состав рекомендаций, а не конкретную формулировку ответа.

### Цель

Научить систему достигать цели через несколько наблюдаемых шагов и проверять результат независимо от текста LLM.

### Что понять

- разницу между историей диалога и рабочим состоянием запуска;
- идемпотентность и повторяемость;
- state-based acceptance tests;
- влияние описаний инструментов и системных инструкций на планирование;
- стоимость лишних шагов.

### Что реализовать

- Получение последних `finished` книг через существующий read tool.
- Tool поиска кандидатов в локальном каталоге по жанрам/тегам.
- Явное исключение книг, уже находящихся в библиотеке.
- Рабочие метаданные запуска: goal, completed actions и доступный step budget.
- Дедупликацию результатов по стабильному `book_id`.
- Идемпотентное поведение write tools при безопасном повторе запроса.
- Acceptance-проверки итоговой БД и списка рекомендаций.

### Практические упражнения

1. Попросить три книги, похожие на последние прочитанные.
2. Добавить одного кандидата в библиотеку и повторить запрос.
3. Сравнить трассы двух разных системных инструкций на одном fake-сценарии.

### Тесты

- Unit: фильтр удаляет книги, уже имеющиеся в библиотеке.
- Unit: кандидаты дедуплицируются по ID, а не только названию.
- Scenario: scripted fake вызывает ожидаемую последовательность read tools.
- Acceptance: результат содержит три допустимых новых ID.
- **Негативный:** при недостатке кандидатов агент честно возвращает меньше трёх, не выдумывая ID.
- **Негативный:** повтор write-вызова не создаёт вторую запись.

### Критерии готовности

- Все четыре MVP-сценария выполняются через backend API.
- Рекомендации проверяются структурированными инвариантами.
- Одинаковый запрос не повреждает состояние при повторной доставке.
- Трасса объясняет, какие данные использованы для результата.

### Вопросы для самопроверки

- Что хранится в рабочем состоянии, а что можно восстановить из шагов?
- Почему нельзя оценивать рекомендацию только сравнением полного текста?
- Какие операции должны быть идемпотентными?
- Как определить, что модель вызвала лишний инструмент?

**Контрольная точка:** backend MVP завершён. RAG, PostgreSQL и frontend для этого не нужны.

**Мои заметки — этап завершён 5 августа 2026:**

- Рекомендация выполняется наблюдаемой цепочкой
  `get_user_library(status=finished, recent_first=true)` →
  `find_similar_books` → финальный ответ.
- Локальный baseline ранжирует кандидатов по числу уникальных общих тегов,
  исключает исходные книги и всю библиотеку пользователя, дедуплицирует по UUID
  и стабилизирует равные оценки через `book_id`.
- Acceptance-тест проверяет существование и уникальность IDs, отсутствие книг
  из библиотеки, ненулевые score/matched tags, порядок tools и согласованность
  trace с working state. Точный текст модели не сравнивается.
- Негативные сценарии подтверждают, что уже добавленный кандидат исключается,
  а недостаток вариантов не компенсируется выдуманными IDs.
- `AgentWorkingState` отдельно хранит цель, подтверждённые действия и бюджет;
  полные аргументы, outputs и ошибки остаются в `AgentStep` trace.
- Агентный `add_book` идемпотентен для точного повтора через `changed=false`, но
  строгий HTTP endpoint сохраняет `409`, а другой статус остаётся конфликтом.
- Все четыре MVP-сценария проходят через backend API со scripted fake без сети.
- Проверка: 137 тестов проходят; чистая SQLite поднимается миграциями до
  `20260803_04`; `alembic check` не обнаруживает расхождений.

**Ответы для самопроверки:**

- Рабочее состояние — компактная backend-проекция цели, успешных действий и
  бюджета; подробности и доказательства можно восстановить из шагов trace.
- Полный текст не является стабильным контрактом: качество результата
  проверяется по UUID и доменным инвариантам, а формулировка остаётся свободной.
- Write-операции должны безопасно переносить повторную доставку, если повтор не
  выражает новое намерение; конфликтующее состояние нельзя скрывать как no-op.
- Лишним считается tool call, который не добавил данных, не изменил состояние и
  не был нужен для исправления контролируемой ошибки; это видно из trace.

## Этап 6. Human-in-the-loop

Подробный порядок реализации: [микро-роадмап этапа 6](./STAGE_6_MICRO_ROADMAP.md).

### Наблюдаемый результат

Защищённое write/destructive-действие переводит запуск в `waiting_for_approval`. После подтверждения оно выполняется ровно один раз, после отклонения состояние данных не меняется.

### Цель

Освоить безопасную паузу и возобновление агента вокруг действий с побочными эффектами.

### Что понять

- классификацию read/write/destructive tools;
- approval как состояние запуска, а не диалоговую условность;
- optimistic locking или другой механизм конкурентного контроля;
- idempotency key;
- доверительную границу между предложением модели и решением пользователя.

### Что реализовать

- Политику выполнения для каждой категории tools.
- Статус `waiting_for_approval`.
- Сохраняемый `PendingAction`: run ID, tool name, проверенные arguments, summary, created/expiry time и idempotency key.
- Endpoints подтверждения и отклонения.
- Возобновление loop с результатом подтверждённого или отклонённого действия.
- Защиту от повторного подтверждения и устаревшей версии запуска.
- Тестовый destructive tool, например удаление записи из библиотеки; включать его модели только в сценариях этого этапа.

### Практические упражнения

1. Подтвердить действие и проверить единственный побочный эффект.
2. Отклонить действие и позволить агенту сформировать финальный ответ.
3. Отправить два одинаковых запроса подтверждения одновременно.

### Тесты

- Unit: read tool выполняется без approval согласно политике.
- Integration: защищённый tool не выполняется до подтверждения.
- Integration: approve выполняет сохранённые проверенные arguments, а не новые аргументы модели.
- Integration: reject не меняет библиотеку.
- **Негативный:** повторный approve не повторяет побочный эффект.
- **Негативный:** approve чужого, истёкшего или уже завершённого run отклоняется.

### Критерии готовности

- Pending action переживает перезапуск backend.
- До approval в БД нет целевого изменения.
- Повторный запрос безопасен.
- Трасса отличает предложение, решение пользователя и исполнение.

### Вопросы для самопроверки

- Почему нельзя хранить pending action только в памяти процесса?
- Какие аргументы должны исполняться после подтверждения?
- Чем approval отличается от сообщения пользователя «да»?
- Какие write tools можно разрешить автоматически и почему?

**Мои заметки — этап завершён 13 августа 2026:**

- `read` и обычные `write` tools выполняются автоматически, а `destructive`
  сначала превращается в сохраняемый `PendingAction`. Модель только предлагает
  действие; право на эффект выдаёт backend после решения пользователя.
- Pending action хранит проверенные arguments, безопасный summary, владельца,
  версию run, срок действия и idempotency key. Поэтому ожидание переживает новый
  HTTP-запрос, новую DB session и перезапуск процесса.
- Approve и reject принимают только пустой объект. Клиент не может подменить
  сохранённые arguments во время подтверждения.
- Approve атомарно захватывает pending action до вызова handler. Из двух
  параллельных запросов только один выполняет эффект; второй читает сохранённый
  результат как replay. Reject сохраняет связанный `user_rejected` ToolResult и
  не вызывает handler.
- Expired action сохраняется как `expired`, чужой action выглядит как
  отсутствующий, а устаревшие status/version не дают выполнить эффект.
- Trace связывает proposal, решение и результат через один `tool_call_id`.
  Approve добавляет completed action, reject — нет.
- Два acceptance-теста проходят полный HTTP-путь approve/reject через три
  отдельных клиента и новые DB sessions. Повтор после «рестарта» не вызывает
  provider и handler ещё раз.
- Финальная проверка обнаружила рассинхронизацию: ORM уже знала статус
  `waiting_for_approval`, а старая миграция оставляла более короткий enum-тип.
  Ревизия `20260812_07` выровняла схему без потери данных; `alembic check` теперь
  входит в автоматический migration-тест.
- Проверка: `185 passed`; чистая база и обновление с предыдущей ревизии доходят
  до head; `alembic check` сообщает `No new upgrade operations detected`;
  локальный HTTP-smoke подтвердил approve, reject и replay без внешней сети.

Ответы на самопроверку:

- Pending action нельзя хранить только в памяти: пользователь может ответить
  после рестарта backend, когда прежних Python-объектов уже нет.
- После approve исполняются только проверенные arguments, сохранённые при
  предложении. Новые arguments из запроса подтверждения не принимаются.
- Approval — это состояние и авторизованное решение с ID, версией, сроком и
  результатом. Сообщение «да» — неоднозначный текст, который модель может
  связать не с тем действием.
- Автоматически допустимы `read` и те `write`, чей ожидаемый эффект обратим и
  разрешён продуктовой политикой. Необратимые или опасные операции требуют
  явного решения пользователя.

## Этап 10. Evals и observability

### Наблюдаемый результат

Одна команда прогоняет фиксированный набор сценариев, выдаёт метрики по выбору tools, аргументам, итоговому состоянию и числу шагов. Для каждого провала можно открыть полную безопасную трассу.

### Цель

Перейти от впечатления «агент вроде работает» к воспроизводимому измерению качества.

### Что понять

- unit, integration, scenario и model-based evals;
- детерминированные и статистические проверки;
- expected, optional и forbidden tools;
- baseline, regression и выбор фиксированной выборки;
- tracing, privacy, redaction, latency и token usage.

### Что реализовать

- Версионируемый dataset минимум из 20 разнообразных сценариев.
- Для каждого примера: input, initial state, expected/optional/forbidden tools, ожидаемые аргументы-инварианты, final-state assertions и max steps.
- Runner для fake-провайдера как обязательный CI-набор.
- Отдельный opt-in runner для реальных моделей.
- Метрики: task success, tool precision/recall где применимо, invalid arguments, forbidden calls, step count, latency и tokens/cost при доступности.
- Трассу: run ID, model/provider, prompt version, step, tool, redacted arguments/result, error, latency, usage и final status.
- Redaction секретов и чувствительного содержимого.
- Сравнение двух провайдеров или двух prompt versions на одном dataset без изменения критериев.

Пример записи eval dataset:

```json
{
  "id": "add-dune-want-to-read",
  "input": "Добавь Дюну в список на чтение",
  "expected_tools": ["search_books", "add_book"],
  "optional_tools": [],
  "forbidden_tools": ["delete_book"],
  "max_steps": 4,
  "final_state": {
    "library_contains": {
      "title": "Дюна",
      "status": "want_to_read"
    }
  }
}
```

### Практические упражнения

1. Превратить один реальный баг в постоянный regression case.
2. Сравнить два системных промпта на неизменном dataset.
3. Найти сценарий, где правильный текст скрывает неправильное состояние БД.

### Тесты

- Unit: evaluator корректно считает expected и forbidden calls.
- Unit: redaction удаляет API keys и отмеченные sensitive fields.
- Integration: trace сохраняется и для успешного, и для упавшего run.
- Regression: набор критических сценариев имеет нулевые forbidden calls.
- **Негативный:** красивый ответ при неверном final state оценивается как failure.
- **Негативный:** превышение max steps не считается частичным успехом.

### Критерии готовности

- Dataset хранится рядом с кодом и имеет версию.
- CI не зависит от платного API.
- Реальные model evals запускаются явно и записывают model/prompt version.
- Любую неуспешную оценку можно связать с trace.
- Логи не содержат секретов.

## Этап 11. Финальная ревизия

### Наблюдаемый результат

Проект имеет актуальную архитектурную карту, список известных ограничений, воспроизводимый демо-сценарий и обоснованное решение о следующем техническом шаге.

### Цель

Закрепить изученное и оценить, какую сложность теперь действительно стоит добавить.

### Что понять

- границы доверия и доступа;
- coupling между доменом, harness и провайдером;
- стоимость поддержки собственных абстракций;
- критерии выбора Agents SDK или графового workflow;
- отличие учебной готовности от production readiness.

### Что реализовать

- Провести ревизию зависимостей между слоями.
- Проверить allowlist tools, validation, approvals, idempotency и user scoping.
- Обновить README по фактическим командам и структуре.
- Описать известные ограничения, threat model и неразрешённые риски.
- Подготовить один воспроизводимый end-to-end demo.
- Зафиксировать baseline evals.
- Написать короткое architecture decision record: оставить самописный loop, перейти на Agents SDK или использовать графовый фреймворк.

### Практические упражнения

1. Нарисовать реальный поток одного write-запроса от UI до БД и обратно.
2. Удалить или упростить одну абстракцию, которая не оправдала себя.
3. Объяснить проект другому разработчику без демонстрации исходного промпта.

### Тесты и проверки

- Полный автоматический набор проходит с чистого checkout.
- Миграции поднимают чистую базу.
- E2E demo выполняет read, многошаговый и approval-сценарии.
- Security check подтверждает отсутствие обхода registry и user scope.
- **Негативный:** попытка вызвать запрещённый tool или получить чужие данные остаётся без побочного эффекта.
- Документированные команды запуска совпадают с реальными.

### Критерии готовности

- Все четыре MVP-сценария воспроизводимы.
- Для каждого запуска доступна безопасная трасса.
- Критические правила покрыты негативными тестами.
- Документация описывает фактическую систему, а не первоначальные намерения.
- Решение о фреймворке основано на конкретных недостатках текущего loop.

## Чего не делать раньше времени

До финальной ревизии не нужны multi-agent orchestration, MCP, browser automation, сложный planner, автоматическая self-reflection или долговременная автономная работа. Они не запрещены навсегда: их следует добавлять только после того, как появится измеримая проблема, которую базовый harness не решает.

## Итоговая проверка обучения

Проект можно считать успешно завершённым, если разработчик способен без подсказки:

1. объяснить, почему модель не выполняет tool сама;
2. нарисовать один полный проход agent loop;
3. добавить новый tool со схемой, политикой и тестами;
4. безопасно остановить и возобновить write-действие;
5. отличить историю, рабочее состояние и RAG-память;
6. превратить найденный сбой в regression eval;
7. по трассе определить, ошиблась модель, инструмент или внешний сервис;
8. аргументированно решить, нужен ли проекту агентный фреймворк.
