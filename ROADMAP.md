# Roadmap Book Agent

План развития после завершения учебной версии. Документ отвечает на три вопроса:
что делать дальше, в каком порядке и когда пункт можно считать закрытым. Даты
намеренно не проставлены: приоритет важнее календаря.

- **Текущая версия:** учебный MVP, не production-ready.
- **Обновлено:** 2026-10-26.
- **Фокус:** сначала безопасность и надёжность, затем качество, затем
  эксплуатация и продуктовые эксперименты.

## Как читать приоритеты

| Приоритет | Значение | Правило |
| --- | --- | --- |
| `P0` | Блокирует безопасное использование несколькими людьми | Не начинать продуктовые задачи, пока P0 не закрыт |
| `P1` | Нужен для надёжной ежедневной работы | Делать после P0, можно параллелить внутри уровня |
| `P2` | Нужен для эксплуатации и роста | После стабилизации P1 |
| `P3` | Продуктовые гипотезы | Только после проверки спроса и метрик |

Размеры: `S` — до нескольких дней, `M` — 1–2 недели, `L` — 2–4 недели,
`XL` — больше месяца или требует отдельного дизайна.

## Текущее состояние

**Работает:**

- 4 MVP-сценария через HTTP и React;
- 7 инструментов с allowlist и строгими Pydantic-схемами;
- approval для destructive-действий с идемпотентностью и TTL;
- SQLite и PostgreSQL, Alembic, seed;
- Open Library с timeout, retry, кэшем и локальным fallback;
- заметки, preferences и лексический retrieval;
- 267 backend-тестов, 39 frontend-тестов, 21 eval-сценарий;
- безопасные трассы и воспроизводимый demo.

**Не готово к реальному использованию:**

- нет аутентификации: все запросы идут от `DEMO_USER_ID`;
- agent loop синхронный, без очереди, streaming и отмены;
- retrieval лексический, без embeddings;
- evals на fake-провайдере не доказывают качество реальной модели;
- нет CI-гейта, деплоя, мониторинга, бэкапов и rate limits;
- raw-трейсы хранят полную историю без политики retention.

## P0 — безопасность и блокеры

### P0.1. Аутентификация, сессии и tenant isolation

**Проблема:** `DEMO_USER_ID` — учебная подмена. Любой клиент видит одну и ту же
библиотеку, а API не различает пользователей.

**Результат:** пользователь входит в систему, все данные привязаны к его
identity, межпользовательский доступ невозможен.

**Критерии приёмки:**

- есть регистрация/вход и защищённые сессии (например, OIDC или email + пароль);
- `user_id` берётся только из проверенной сессии, не из настроек и не из тела
  запроса;
- каждый repository-запрос фильтрует данные по tenant/user;
- интеграционный тест на двух пользователей: чужой run, action, note, library
  entry и preference возвращают `404` или `403`, но не данные;
- `DEMO_USER_ID` удалён из production-конфигурации или явно ограничен dev-режимом;
- README и threat model обновлены.

**Зависимости:** нет. **Размер:** L.

### P0.2. Сквозной аудит авторизации

**Проблема:** ownership-проверки размазаны по endpoint'ам и сервисам; новый
endpoint легко добавить без проверки.

**Результат:** единая точка принятия решения об авторизации и тесты, которые
ловят забытые проверки.

**Критерии приёмки:**

- описан и реализован единый authz-контракт для HTTP и tool handlers;
- чужой ресурс неотличим от несуществующего;
- тест-матрица покрывает все endpoint'ы и все user-scoped tools;
- попытка обратиться к чужому `PendingAction` не раскрывает его существование;
- в security contract добавлены негативные сценарии.

**Зависимости:** P0.1. **Размер:** M.

### P0.3. Rate limits, бюджет LLM и защита API

**Проблема:** один клиент может исчерпать лимиты провайдера или завалить сервис
дорогими запусками.

**Результат:** предсказуемая стоимость и устойчивость к злоупотреблению.

**Критерии приёмки:**

- лимиты на пользователя и IP для agent runs и write-endpoint'ов;
- ограничение параллельных запусков и дневного token/cost-бюджета;
- понятные `429`/`402`-ответы без внутренних деталей;
- CORS и security headers настроены для известных origin'ов;
- лимиты конфигурируются через env и покрыты тестами.

**Зависимости:** P0.1. **Размер:** M.

### P0.4. Политика хранения и защиты трасс

**Проблема:** raw `AgentRun` содержит сообщения и tool results; safe trace
редактирует данные, но retention, audit-доступ и шифрование не определены.

**Результат:** понятная политика: что храним, сколько, кто читает и как удаляем.

**Критерии приёмки:**

- сроки хранения raw и safe traces заданы и применяются фоновой задачей;
- чувствительные поля шифруются или не сохраняются;
- доступ к raw trace отделён от обычного API и аудируется;
- есть тест на удаление/экспирацию и на отсутствие секретов в safe trace;
- threat model обновлён.

**Зависимости:** P0.1. **Размер:** M.

### P0.5. CI-гейт и фиксация toolchain

**Проблема:** frontend-тесты падают на Node 26 из-за jsdom opaque origin;
проверки запускаются вручную и могут разойтись с README.

**Результат:** одинаковые проверки локально и в CI, воспроизводимое окружение.

**Критерии приёмки:**

- CI запускает backend tests, frontend tests, build, lint и eval baseline;
- версии Python и Node зафиксированы (Node 22 или исправлен jsdom-конфиг для 26);
- PR не проходит при падении любого гейта;
- README содержит ровно те команды, которые выполняет CI;
- добавлен `git diff --check` или аналог для документов.

**Зависимости:** нет. **Размер:** S–M.

## P1 — надёжность ядра

### P1.1. Асинхронные запуски и очередь

**Проблема:** agent loop выполняется внутри HTTP-запроса и удерживает worker;
долгие и параллельные запуски деградируют.

**Результат:** `POST /api/agent/runs` создаёт запуск и быстро возвращает `202`;
выполнение идёт в worker'е, статус доступен через API.

**Критерии приёмки:**

- есть durable queue (например, Redis + worker) и идемпотентный enqueue;
- создание запуска не блокируется на LLM;
- `GET /api/agent/runs/{id}` отражает прогресс;
- падение worker'а не теряет запуск: есть retry и восстановление;
- несколько процессов не выполняют один запуск дважды;
- нагрузочный тест подтверждает отсутствие блокировки HTTP.

**Зависимости:** P0.1. **Размер:** XL.

### P1.2. Streaming, отмена и таймауты

**Проблема:** пользователь ждёт весь ответ; отменить запуск нельзя.

**Результат:** события шагов приходят по SSE/WebSocket, запуск можно отменить,
зависший provider не держит ресурсы бесконечно.

**Критерии приёмки:**

- SSE-канал отдаёт события `step`, `tool`, `approval_required`, `completed`,
  `failed`;
- отмена переводит запуск в `cancelled` и не оставляет выполняющийся handler;
- таймауты на модель, каталог и весь запуск;
- frontend показывает прогресс и корректно переподключается;
- тесты на отмену до и после side effect.

**Зависимости:** P1.1. **Размер:** L.

### P1.3. Общая идемпотентность и retry-политика

**Проблема:** идемпотентность хорошо решена для approval, но не является общим
контрактом write-операций и повторных HTTP-запросов.

**Результат:** повтор запроса не создаёт дубликаты и не применяет эффект дважды.

**Критерии приёмки:**

- idempotency key для всех write-endpoint'ов и tool calls;
- повтор с тем же ключом возвращает сохранённый результат;
- конфликт ключей с разными аргументами возвращает `409`;
- retry безопасен для read и write;
- политика описана в архитектуре и покрыта тестами.

**Зависимости:** P1.1. **Размер:** M.

### P1.4. Live-evals и quality gate

**Проблема:** fake-evals проверяют код, но не качество реальной модели; один
ручной live-run не даёт статистики.

**Результат:** регулярный прогон на реальной модели с порогами качества,
стоимости и latency.

**Критерии приёмки:**

- dataset расширен до реалистичных формулировок и негативных кейсов;
- live-run запускается по расписанию и по запросу;
- отчёт сравнивается с baseline автоматически;
- заданы пороги task success, tool precision/recall и forbidden calls;
- regression блокирует merge или требует явного решения;
- стоимость и latency видны в отчёте.

**Зависимости:** P0.5, P1.1. **Размер:** L.

### P1.5. Качество рекомендаций

**Проблема:** рекомендации строятся по пересечению тегов; качество не измеряется
отдельно от успешности сценария.

**Результат:** измеримое качество подбора и объяснимость рекомендаций.

**Критерии приёмки:**

- offline-метрики рекомендаций (precision@k, diversity, novelty);
- исключение уже прочитанных и нерелевантных книг;
- объяснение через реальные `matched_tags`, без выдуманных книг;
- A/B- или ручная оценка на наборе сценариев;
- деградация метрик видна в evals.

**Зависимости:** P1.4. **Размер:** M.

## P1 — память и каталог

### P1.6. Hybrid retrieval по заметкам

**Проблема:** лексический поиск не находит перефразирования и синонимы.

**Результат:** embeddings + лексический поиск с reranking и цитированием
источников.

**Критерии приёмки:**

- индекс перестраивается при изменении заметки;
- hybrid-поиск возвращает `note_id`, `chunk_id` и score;
- цитаты в ответе соответствуют реально найденным фрагментам;
- evaluation-набор включает перефразирования;
- стоимость embedding-запросов ограничена и кэшируется;
- есть fallback на лексический поиск при недоступности embedding-провайдера.

**Зависимости:** P1.4. **Размер:** L.

### P1.7. Устойчивость внешнего каталога

**Проблема:** fallback и кэш работают в одном процессе; нет circuit breaker и
общего кэша.

**Результат:** предсказуемое поведение при деградации Open Library.

**Критерии приёмки:**

- circuit breaker с понятными состояниями и метриками;
- общий кэш между процессами (например, Redis) с TTL и ограничением размера;
- rate-limit coordination для внешнего API;
- `degraded=true` и источник видны в ответе и trace;
- тесты на timeout, 429, 5xx и восстановление.

**Зависимости:** P1.1. **Размер:** M.

## P2 — эксплуатация и масштабирование

### P2.1. Деплой и окружения

**Проблема:** проект запускается только локально; нет воспроизводимого
production-окружения.

**Результат:** контейнеры, конфигурация окружений, миграции при деплое.

**Критерии приёмки:**

- Dockerfile для backend и frontend;
- staging и production конфигурации без секретов в образе;
- миграции выполняются отдельным шагом и откатываются;
- health/readiness endpoints;
- деплой описан в README.

**Зависимости:** P0.5. **Размер:** L.

### P2.2. Мониторинг и алерты

**Проблема:** нет метрик, по которым можно понять деградацию.

**Результат:** видимость latency, ошибок, стоимости и состояния очереди.

**Критерии приёмки:**

- метрики HTTP, LLM, tools, очереди и БД;
- алерты на error rate, latency, budget и застрявшие запуски;
- correlation по `run_id` в логах;
- дашборд для основных сценариев;
- runbook на типовые инциденты.

**Зависимости:** P1.1, P2.1. **Размер:** M.

### P2.3. Бэкапы, восстановление и нагрузка

**Проблема:** нет гарантий сохранности данных и понимания пределов системы.

**Результат:** проверенное восстановление и известная ёмкость.

**Критерии приёмки:**

- регулярные бэкапы PostgreSQL и тест восстановления;
- RPO/RTO зафиксированы;
- нагрузочный тест с целевыми latency/throughput;
- найдены и устранены узкие места;
- disaster recovery описан.

**Зависимости:** P2.1. **Размер:** M–L.

## P3 — продуктовые гипотезы

Каждый пункт — гипотеза, а не обязательство. Перед реализацией нужна метрика
успеха и понимание, какую проблему пользователя она решает.

### P3.1. Импорт и экспорт библиотеки

**Гипотеза:** без быстрого импорта новый пользователь не увидит ценность и уйдёт.

**Метрика:** time-to-first-value, доля завершённых импортов, retention после
первой недели.

**Критерии приёмки:** CSV/Goodreads-импорт с отчётом об ошибках, экспорт без
потери данных, dry-run и откат.

**Размер:** M.

### P3.2. Цели чтения и статистика

**Гипотеза:** цели и прогресс повышают возвращаемость.

**Метрика:** weekly active users, доля пользователей с активной целью, возвраты
на второй и четвёртой неделе.

**Критерии приёмки:** цель на период, прогресс, напоминания с учётом согласия,
приватность по умолчанию.

**Размер:** M.

### P3.3. Интеграции с книжными сервисами

**Гипотеза:** синхронизация с внешней библиотекой снижает ручной ввод.

**Метрика:** доля пользователей с подключённой интеграцией, снижение ручных
операций.

**Критерии приёмки:** один провайдер, явное согласие, обработка отзыва доступа,
идемпотентная синхронизация.

**Размер:** L.

### P3.4. Улучшение интерфейса и мобильный сценарий

**Гипотеза:** текущий UI функционален, но не оптимизирован под ежедневное
использование с телефона.

**Метрика:** completion rate сценариев с мобильного, число брошенных запусков.

**Критерии приёмки:** адаптивная вёрстка, доступность с клавиатуры и
screen reader, ускорение основного сценария.

**Размер:** M.

### P3.5. Публичный API и совместные списки

**Гипотеза:** пользователям нужны общие списки и автоматизация.

**Метрика:** число активных интеграций, доля общих списков, удержание.

**Критерии приёмки:** токены с ограниченными scopes, rate limits, отзыв доступа,
аудит действий, приватность по умолчанию.

**Размер:** L.

## Вехи

### M1 — Safe multiuser MVP

**Входит:** P0.1–P0.5.

**Выход:** несколько пользователей могут безопасно работать одновременно;
чужие данные недоступны; CI и toolchain воспроизводимы.

### M2 — Async agent

**Входит:** P1.1–P1.3.

**Выход:** запуски не блокируют HTTP, поддерживают прогресс, отмену и
восстановление; write-операции идемпотентны.

### M3 — Quality

**Входит:** P1.4–P1.7.

**Выход:** live-evals с порогами, hybrid retrieval, устойчивый каталог,
измеримое качество рекомендаций.

### M4 — Operations & product

**Входит:** P2.1–P2.3 и выбранные P3-гипотезы.

**Выход:** воспроизводимый деплой, мониторинг, бэкапы; продуктовые эксперименты
запускаются только с метрикой и планом отката.

## Non-goals

Сознательно не делаем, пока нет подтверждённой потребности:

- multi-agent оркестрацию и handoff между агентами;
- MCP и универсальный tool marketplace;
- browser/computer automation;
- автономные фоновые задачи на часы;
- собственный сложный planner;
- векторную базу «для всей памяти» без evaluation;
- self-reflection и автоматическое переписывание промптов;
- замену собственного loop на framework ради моды.

Триггеры пересмотра orchestration описаны в
[ADR-001](./docs/adr/001-agent-orchestration.md). Если появляется новый триггер,
сначала фиксируется измеряемая проблема, затем решение, затем миграция с
прогоном того же versioned dataset и security contract.

## Definition of Done

Пункт roadmap считается закрытым, только если:

1. реализован пользовательский или инженерный результат, а не только код;
2. есть позитивные и негативные тесты;
3. обновлены README, архитектура и threat model, если изменились запуск,
   границы доверия или риски;
4. пройдены backend/frontend проверки и eval baseline;
5. для P0/P1 описано наблюдаемое поведение при ошибке;
6. изменение можно откатить;
7. в commit message и PR объяснено, какую проблему закрывает изменение.

## Порядок пересмотра

Roadmap пересматривается после каждой вехи и при появлении нового blocking
риска. Правила простые:

- P0 имеет приоритет над любым продуктовым пунктом;
- новый пункт добавляется с проблемой, критериями приёмки и метрикой;
- завершённый пункт удаляется из активного списка, а не остаётся «на всякий
  случай»;
- если пункт не начат за два цикла и не блокирует другие, он возвращается в
  обсуждение, а не висит в статусе «запланировано».
