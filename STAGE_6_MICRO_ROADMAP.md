# Этап 6: микро-роадмап

Этот документ разбивает этап «Human-in-the-loop» на небольшие проверяемые
итерации. Мы проходим их строго по порядку. После каждой итерации приложение
остаётся рабочим, а все ранее реализованные сценарии продолжают проходить.

Вернуться к общей карте: [ROADMAP.md](./ROADMAP.md).

## Граница этапа

Целевой сценарий:

> Удали «Дюну» из моей библиотеки.

Ожидаемая цепочка:

1. модель предлагает вызов destructive tool с идентификатором записи;
2. backend валидирует аргументы, но не вызывает обработчик;
3. запуск получает статус `waiting_for_approval`, а действие сохраняется в БД;
4. пользователь видит сформированное backend описание действия;
5. approve исполняет именно сохранённые аргументы ровно один раз;
6. reject не меняет библиотеку;
7. agent loop получает результат решения и может завершить ответ;
8. trace отдельно показывает предложение, решение и исполнение.

На этом этапе мы не строим универсальный workflow engine, очередь фоновых
задач, frontend, произвольные approval-цепочки и распределённые транзакции.
Один запуск может ожидать одно явно описанное действие. Такой предел позволяет
изучить доверительную границу и конкурентный контроль без лишней платформенной
инфраструктуры.

## Принятые решения

- `READ` и существующий `WRITE` выполняются автоматически. Это сохраняет
  работающий MVP: добавление книги и изменение статуса не начинают неожиданно
  требовать подтверждения.
- Новая категория `DESTRUCTIVE` всегда требует approval. Первым таким tool
  будет удаление записи из библиотеки.
- Модель только предлагает действие. Решение о необходимости approval принимает
  backend по метаданным зарегистрированного tool, а не по его названию или
  текстовому описанию.
- После approve исполняются проверенные аргументы из `PendingAction`. Endpoint
  подтверждения не принимает замену аргументов.
- Описание для пользователя формирует backend из проверенных данных. Текст
  модели не является доверенным описанием побочного эффекта.
- На этом этапе один модельный шаг не может смешивать approval-required tool с
  другими tool calls. Неоднозначный пакет отклоняется целиком до побочных
  эффектов.

## Рабочий договор для каждой итерации

Каждый микроэтап заканчивается отдельным коммитом и отчётом:

1. **Что сделано:** изменённые контракты, поток данных и наблюдаемый результат.
2. **Зачем это нужно:** какую конкретную угрозу или неопределённость устраняет
   изменение.
3. **На что обратить внимание:** инварианты, компромиссы и типичные ошибки.
4. **Как проверено:** названия тестов, команды и фактический результат.
5. **Советы на будущее:** что станет важно позже, но не должно усложнять текущий
   шаг.
6. **Самоконтроль:** ответы на вопросы своими словами до перехода дальше.

Если критерий готовности не выполнен, микроэтап не считается завершённым.

## 6.1. Политика approval и безопасная подготовка tool call

### Результат итерации

Backend однозначно определяет, какие tools требуют решения пользователя, и
умеет проверить аргументы tool без запуска его обработчика.

### Что реализуем

- Расширим `ToolAccess` категорией `DESTRUCTIVE`.
- Введём небольшую явную политику `requires_approval(access)`:
  - `READ` → нет;
  - `WRITE` → нет;
  - `DESTRUCTIVE` → да.
- Разделим текущую операцию registry на две части:
  1. найти tool и провалидировать вход через его Pydantic-схему;
  2. исполнить уже подготовленный вызов.
- Оставим удобный метод полного исполнения для доверенных прямых вызовов и
  существующих тестов.
- Подготовленный вызов содержит ссылку на зарегистрированное определение tool и
  канонические аргументы после Pydantic-валидации.

### Зачем это нужно

Если validation и handler вызываются одной неделимой операцией, agent loop не
может проверить и сохранить действие, не выполнив его. Approval после такого
вызова был бы декоративным: побочный эффект уже произошёл.

### На что обратить внимание

- Категорию задаёт код при регистрации tool, а не модель в arguments.
- Имя вроде `safe_remove` и красивое description ничего не доказывают с точки
  зрения безопасности.
- При ошибке поиска или валидации handler не должен быть вызван ни разу.
- Не нужен настраиваемый язык правил: трёх категорий и одной функции достаточно
  для текущего продукта.
- Канонические аргументы должны сериализоваться одинаково, чтобы позже их можно
  было сохранить и исполнить без повторной интерпретации текста модели.

### Проверка

- Unit: `READ` и `WRITE` не требуют approval, `DESTRUCTIVE` требует.
- Unit: подготовка валидного call не вызывает handler.
- Unit: невалидные arguments дают контролируемую tool-ошибку без handler.
- Regression: прежний полный вызов registry продолжает исполнять существующие
  tools и возвращать прежний контракт.

### Критерий готовности

В тесте destructive call можно провалидировать и получить его канонические
arguments, при этом счётчик вызовов handler остаётся равен нулю.

### Самоконтроль

**Почему нельзя определять необходимость approval по имени tool или его
description?**

Имя и description — текстовые метаданные для модели. Они легко меняются и не
являются исполняемой политикой безопасности. Решение должен принимать backend
по закрытому enum, присвоенному при регистрации доверенного кода.

**Почему недостаточно сначала вызвать tool, а затем спросить пользователя,
согласен ли он?**

Approval защищает границу до побочного эффекта. После удаления запись уже
изменилась, и вопрос превращается в уведомление. Компенсирующее восстановление
не эквивалентно отсутствию действия и само может завершиться ошибкой.

**Почему существующие write-tools пока выполняются автоматически?**

У продукта уже есть согласованный MVP-контракт для добавления книги и изменения
статуса. Этап изучает защищённое destructive-действие; изменение всех write
сценариев увеличит объём без нового учебного результата. Позже политику можно
ужесточить по реальным рискам конкретного действия.

### Совет на будущее

Не превращать `ToolAccess` в оценку риска из десятков уровней, пока нет
нескольких действий с реально различающимися требованиями. Сначала полезнее
иметь маленькую политику, которую невозможно понять двояко.

### Отчёт о завершении 6.1

**Что сделано.** В `ToolAccess` добавлена категория `DESTRUCTIVE`, а функция
`requires_approval` стала единственным явным правилом текущей approval-политики.
Registry теперь сначала выполняет `prepare`: находит зарегистрированный tool и
преобразует сырые arguments модели в строгую Pydantic-модель. Результатом
успешной подготовки становится `PreparedToolCall` со ссылкой на доверенное
определение, типизированными arguments и их JSON-совместимым каноническим
представлением. Отдельный `execute_prepared` вызывает handler и валидирует его
результат. Прежний `execute` сохранён как композиция этих двух операций, поэтому
существующий agent loop и прямые вызовы tools не изменили поведения.

**Зачем.** До этого поиск, validation и побочный эффект происходили внутри
одного метода. В такой конструкции backend не мог остановиться между проверкой
предложения модели и выполнением действия. Новая граница позволяет будущему
agent loop проверить destructive-вызов, показать его пользователю и сохранить,
не изменяя библиотеку.

**На что обратить внимание.** `PreparedToolCall` создаётся из определения,
зарегистрированного доверенным backend-кодом; модель не назначает себе уровень
доступа. Канонические arguments нужны для сохранения данных, но исполняемым
входом остаётся уже провалидированная Pydantic-модель. Ошибка неизвестного tool
или arguments возвращается до handler. При этом 6.1 ещё не блокирует
destructive tools внутри agent loop: production-регистрация удаления появится
только после появления сохраняемой паузы.

**Как проверено.** Тест policy проверяет все три категории доступа. Отдельный
тест готовит искусственный destructive tool, проверяет подстановку значения по
умолчанию в канонические arguments и доказывает, что handler не был вызван.
Невалидные arguments также отклоняются при нулевом числе вызовов handler.
Совместимость полного `execute` покрыта прежними тестами registry и всех tools.
Точечный прогон завершился результатом `20 passed`, полный backend regression —
`142 passed`.

**Что мы выучили.** Tool calling — это предложение модели, а не разрешение на
исполнение. Approval является настоящей защитой только до побочного эффекта.
Политика безопасности должна опираться на доверенные структурированные
метаданные, а validation полезно проектировать как самостоятельную операцию.
Разделение `prepare` и `execute` создаёт точку контроля без изменения уже
работающего публичного контракта.

**Советы на будущее.** В 6.2 нужно тестировать реальное удаление отдельно от
agent loop и не публиковать новый tool production-модели. Не следует пока
добавлять универсальный policy engine, soft delete или произвольные уровни
риска: для текущего сценария они не дают нового проверяемого свойства.

Ответы на содержательные вопросы для самоконтроля приведены выше в разделе
«Самоконтроль». Они проверяют границу доверия, момент approval и осознанное
решение оставить существующие write-tools автоматическими.

## 6.2. Доменное удаление и destructive tool

### Результат итерации

Доменный слой умеет удалить конкретную запись из библиотеки, а строгий tool
предоставляет эту операцию registry. В production agent loop tool пока не
регистрируется: approval-защита появится в следующей итерации.

### Что реализуем

- Добавим в repository удаление записи по `user_id` и `book_id`.
- Добавим в `BookService` операцию удаления с проверкой принадлежности записи
  пользователю.
- Определим строгие `RemoveBookArguments` и `RemoveBookResult`.
- Вернём в результате минимальный снимок удалённой записи, необходимый для
  понятного tool result и трассы.
- Зарегистрируем tool как `DESTRUCTIVE` только в изолированных unit/integration
  тестах этой итерации.
- Ошибку отсутствующей записи преобразуем в контролируемую доменную/tool-ошибку.

### Зачем это нужно

Approval-механизм нельзя проверять на фиктивном счётчике до конца этапа: нужен
настоящий, наблюдаемый побочный эффект. Но подключать его модели до появления
паузы опасно, поэтому доменная операция сначала тестируется отдельно.

### На что обратить внимание

- Tool не содержит SQL и не обходит `BookService`.
- `user_id` берётся из доверенного контекста выполнения, а не из аргументов
  модели.
- Удаляется запись библиотеки, а не книга из общего каталога.
- Повторное прямое удаление не считается идемпотентным успехом: именно слой
  approval позже предотвращает повторное исполнение одного решения.
- Не добавляем soft delete без требования восстановления или аудита удалённых
  записей; trace уже фиксирует действие.

### Проверка

- Service integration: пользователь удаляет собственную запись.
- Негативный: нельзя удалить отсутствующую или чужую запись.
- Tool integration: валидный прямой вызов возвращает снимок и удаляет запись.
- Негативный: невалидный UUID и лишние поля отклоняются до service.
- Regression: каталог книг не меняется после удаления из библиотеки.

### Критерий готовности

Операция полностью тестируется через service и прямой вызов registry, но
production-набор tools, доступный модели, ещё не содержит `remove_book`.

### Самоконтроль

**Почему destructive tool полезно сначала проверить отдельно от agent loop?**

Так мы разделяем две причины ошибки: бизнес-операцию удаления и механику паузы.
Если сквозной тест упадёт позже, уже будет известно, что доменная операция сама
по себе корректна и соблюдает границу пользователя.

**Зачем возвращать снимок удалённой записи, если её уже нет в таблице?**

Результат позволяет модели и trace точно объяснить, что было удалено, не делая
запрос к уже отсутствующей строке. Снимок должен быть минимальным и не включать
лишние пользовательские данные.

**Почему сейчас не нужен soft delete?**

Soft delete добавляет фильтры почти во все запросы, правила восстановления и
новые состояния данных. Текущая задача — безопасно подтвердить необратимое для
MVP действие. Если появится продуктовая корзина или юридическое хранение, это
станет отдельным требованием.

### Совет на будущее

При появлении нескольких destructive tools выносить общий код следует только
для реально повторяющегося поведения. Доменная проверка удаления книги и,
например, удаления аккаунта почти наверняка будет различаться.

## 6.3. Сохраняемое ожидающее действие

### Результат итерации

Ожидающее решение действие хранится в БД и переживает создание нового процесса
или SQLAlchemy session. Запуск получает явное состояние ожидания и версию для
конкурентного контроля.

### Что реализуем

- Добавим `WAITING_FOR_APPROVAL` в `AgentRunStatus`.
- Добавим к запуску целочисленную `version`, увеличиваемую при значимых
  переходах состояния.
- Создадим модель `PendingAction` и миграцию со следующими данными:
  - `id`, `run_id`, `user_id`, `tool_call_id`, `tool_name`;
  - канонические validated arguments в JSON;
  - сформированный backend `summary`;
  - статус `pending`, `approved`, `rejected` или `expired`;
  - уникальный `idempotency_key`;
  - `created_at`, `expires_at`, `resolved_at`;
  - ожидаемая версия запуска.
- Добавим repository-операции создания и чтения pending action.
- Установим один понятный срок жизни, например 15 минут, через настройку
  приложения.
- Обеспечим максимум одно активное pending action на запуск.

### Зачем это нужно

Ожидание — долговечное состояние бизнес-процесса. Если хранить его в словаре
Python, перезапуск backend потеряет аргументы и связь с run, а другой worker не
сможет обработать решение пользователя.

### На что обратить внимание

- В БД попадают результаты строгой валидации, а не сырой JSON модели.
- `summary` не заменяет arguments и никогда не используется для исполнения.
- Секреты не должны попадать ни в arguments, ни в summary, ни в trace.
- Миграция обязана корректно обновить существующую БД с завершёнными runs.
- Уникальный ключ помогает распознать повтор, но сам по себе не обеспечивает
  атомарность побочного эффекта.

### Проверка

- Migration: чистая база поднимается до `head`.
- Migration: обновление с предыдущей ревизии сохраняет книги, библиотеку и
  agent traces.
- Integration: pending action читается в новой session с теми же аргументами.
- Негативный: нельзя создать два активных pending action для одного run.
- Serialization: UUID и enum имеют стабильное JSON-представление.

### Критерий готовности

Тест создаёт pending action, закрывает session, открывает новую и восстанавливает
все данные, достаточные для показа решения и будущего исполнения.

### Самоконтроль

**Почему хранить pending action только в памяти процесса небезопасно?**

Процесс может перезапуститься между предложением и нажатием approve, а запрос
может попасть в другой worker. Память не является общей и долговечной, поэтому
пользователь либо потеряет действие, либо backend будет вынужден просить модель
предложить его заново с потенциально другими аргументами.

**Почему сохраняются именно validated arguments, а не исходный JSON?**

Approval относится к конкретному, уже понятому backend действию. Сырой JSON
может содержать лишние поля, нестабильные формы или значения, которые позже
будут интерпретированы иначе. Каноническая схема фиксирует предмет решения.

**Для чего нужна версия запуска рядом с idempotency key?**

Idempotency key распознаёт повтор одного запроса, а версия обнаруживает, что
состояние run изменилось с момента предложения. Это разные угрозы: дубликат и
устаревшее решение.

### Совет на будущее

Срок жизни стоит сделать настраиваемым, но не строить планировщик фонового
истечения. На текущем масштабе достаточно лениво переводить просроченное
действие в `expired` при чтении или попытке решения.

## 6.4. Пауза agent loop до побочного эффекта

### Результат итерации

Когда модель предлагает destructive call, agent loop сохраняет ожидающее
действие и возвращает `waiting_for_approval`. Обработчик tool не вызывается, и
библиотека остаётся неизменной.

### Что реализуем

- Подключим `remove_book` к набору tools, доступному agent loop.
- Перед исполнением каждого подготовленного call применим approval policy.
- Для destructive call в одной транзакции сохраним:
  - шаг с предложением модели;
  - `PendingAction`;
  - статус и новую версию run.
- Расширим API-ответ запуска данными, необходимыми клиенту для показа approval:
  идентификатор действия, summary и срок действия.
- Запретим смешанный или множественный пакет tool calls, если хотя бы один из
  них требует approval. Вернём контролируемую ошибку
  `ambiguous_approval_batch` без исполнения всего пакета.
- Сформируем summary по validated arguments и данным каталога на backend.

### Зачем это нужно

Это первая итерация, в которой защита становится наблюдаемой: модель уже может
предложить удаление, но ни её предложение, ни генерация summary не дают права
изменить данные.

### На что обратить внимание

- Сначала проверяется весь пакет, затем исполняются разрешённые вызовы. Иначе
  read/write из начала пакета успеют изменить состояние до обнаружения
  destructive call.
- Статус `waiting_for_approval` — состояние run, а не финальная ошибка.
- `tool_call_id` нужен для правильного продолжения истории после решения.
- Snapshot system prompt не должен подменять сохранённое состояние run.
- До approve в trace допустимо событие предложения, но не исполнения.

### Проверка

- Agent integration: fake provider предлагает `remove_book`, run останавливается
  в `waiting_for_approval`.
- Integration: запись библиотеки существует после остановки.
- Integration: handler destructive tool вызван ноль раз.
- API: ответ содержит безопасный summary, ID и expiry без внутренних секретов.
- Негативный: смешанный пакет не исполняет ни один call.
- Restart: pending виден через API из новой session/app instance.

### Критерий готовности

Сквозной backend-тест доводит run до ожидания, подтверждает отсутствие целевого
изменения в БД и восстанавливает pending action после перезапуска контекста.

### Самоконтроль

**Почему approval — состояние запуска, а не сообщение модели «Вы уверены?»?**

Текст не блокирует код: модель может продолжить генерацию или tool может быть
вызван другим путём. Состояние run даёт backend проверяемый запрет на дальнейшее
исполнение до отдельного авторизованного решения.

**Почему смешанный пакет безопаснее целиком отклонить, чем исполнить его
автоматическую часть?**

Частичное исполнение создаёт неочевидный порядок эффектов: пользователь видит
подтверждение одного действия, хотя другие уже произошли. Для первого варианта
протокола атомарно понятный пакет важнее поддержки редкого сложного ответа
модели.

**Почему summary должен строить backend?**

Модель может ошибочно назвать другую книгу или смягчить последствия. Backend
имеет validated ID и доверенный каталог, поэтому способен описать реальный
объект, к которому будет применён handler.

### Совет на будущее

Если реальные сценарии потребуют нескольких approval calls, сначала определить
продуктовую семантику: подтверждать пакет целиком или каждый пункт отдельно.
Не расширять протокол только потому, что API модели технически допускает массив.

## 6.5. Безопасное подтверждение и единственное исполнение

### Результат итерации

Авторизованный пользователь подтверждает pending action отдельным endpoint.
Backend ровно один раз исполняет сохранённые аргументы, фиксирует решение и
побочный эффект, после чего может продолжить run.

### Что реализуем

- Добавим endpoint approve по ID run/action без поля `arguments`.
- Проверим пользователя, статус pending, срок действия и ожидаемую версию run.
- Получим подготовленное определение tool по сохранённому имени и восстановим
  его arguments через строгую схему.
- Выполним удаление и перевод action в `approved`/run в следующее состояние в
  одной транзакционной границе.
- Запишем в trace отдельные события решения и успешного исполнения.
- Повторный approve вернёт стабильный контролируемый результат или conflict, но
  не вызовет handler повторно.
- После фиксации эффекта передадим tool result механизму продолжения loop.

### Зачем это нужно

Между нажатием кнопки и ответом сети возможны повторы, параллельные запросы и
сбой процесса. Система должна связывать согласие пользователя с одним
сохранённым действием, а не повторять удаление при каждом HTTP-запросе.

### На что обратить внимание

- Новый JSON в approve нельзя считать более свежей версией намерения: любые
  заменяющие arguments означают новое действие и требуют нового approval.
- Idempotency key не закрывает crash window между удалением и отметкой
  `approved`. Доменный эффект и разрешение pending должны фиксироваться одной
  DB-транзакцией.
- Существующие service/repository методы могут делать внутренний `commit`; для
  этого пути понадобится контролируемая unit of work или `flush` без раннего
  commit.
- Внешний вызов LLM нельзя включать в DB-транзакцию. Сначала атомарно фиксируем
  действие, затем продолжаем модель.
- Если provider упал после commit, action остаётся исполненным, а повторный
  approve только возобновляет/возвращает состояние и не удаляет повторно.

### Проверка

- Integration: approve удаляет ожидаемую запись по сохранённым arguments.
- Негативный: endpoint не принимает новые arguments.
- Integration: эффект и `approved` фиксируются вместе.
- Негативный: два последовательных approve вызывают handler один раз.
- Failure injection: ошибка provider после commit не отменяет и не повторяет
  подтверждённый эффект.
- Trace: предложение, решение и исполнение различимы.

### Критерий готовности

При повторной доставке approve число исполнений handler остаётся равным одному,
а состояние БД не может содержать удалённую запись вместе с `pending` action.

### Самоконтроль

**Почему approve должен исполнять сохранённые arguments, а не новые значения из
запроса?**

Пользователь подтвердил показанное конкретное действие. Замена ID между показом
и исполнением нарушает предмет согласия и открывает классическую
time-of-check/time-of-use уязвимость.

**Почему одного idempotency key недостаточно для exactly-once эффекта?**

Ключ помогает найти повтор, но при двух независимых commit процесс может
упасть после удаления и до отметки ключа обработанным. Повтор тогда не увидит
завершение. Общая транзакция устраняет промежуточное наблюдаемое состояние.

**Что должно произойти, если LLM недоступна после успешного удаления?**

Удаление и approval остаются успешно зафиксированными. Run может получить
контролируемое состояние ошибки или быть возобновлён позже, но повторный запрос
не должен снова выполнять destructive handler.

### Совет на будущее

Гарантия ровно одного эффекта реальна внутри одной БД. Для внешнего API без
общей транзакции понадобятся idempotency key на стороне провайдера, outbox или
другая явно спроектированная схема доставки.

## 6.6. Отклонение и возобновление agent loop

### Результат итерации

Пользователь может отклонить действие без изменения библиотеки. Agent loop
получает структурированный результат отказа и формирует корректный финальный
ответ либо продолжает безопасное планирование.

### Что реализуем

- Добавим user-scoped endpoint reject по ID run/action.
- Атомарно переведём action в `rejected` и обновим run/version без вызова tool.
- Сформируем синтетический `ToolResult` с кодом `user_rejected`, привязанный к
  исходному `tool_call_id`.
- Для approve используем фактический результат handler, для reject —
  структурированный результат отказа.
- Восстановим историю из сохранённых шагов: assistant tool call, затем
  соответствующий tool result.
- Продолжим бюджет шагов и working state существующего run, не создавая новый.
- Определим поведение при исчерпанном бюджете: решение фиксируется, а run
  завершается контролируемым статусом без дополнительного вызова provider.

### Зачем это нужно

Reject — не ошибка транспорта и не отсутствие ответа. Это полноценное решение
пользователя, которое модель должна увидеть в корректном tool-протоколе, чтобы
не заявить, будто удаление состоялось.

### На что обратить внимание

- Сообщение пользователя «да» или «нет» в обычном чате не заменяет endpoint:
  оно не содержит надёжной связи с pending action и может быть неверно понято.
- Reject никогда не вызывает destructive handler, даже для проверки.
- При восстановлении истории нельзя дублировать старый system snapshot или
  терять assistant tool call.
- Решение пользователя и последующая ошибка модели — разные события trace.
- Повторный reject так же не должен повторно возобновлять loop.

### Проверка

- Integration: reject сохраняет запись библиотеки без изменений.
- Agent integration: provider получает `user_rejected` для исходного
  `tool_call_id` и формирует финальный ответ.
- Негативный: handler не вызывается.
- Негативный: повторный reject не запускает provider повторно.
- Budget: исчерпанный лимит корректно завершает run после фиксации решения.
- History: продолжение удовлетворяет протоколу assistant-tool/tool-result.

### Критерий готовности

Approve и reject продолжают один и тот же persisted run; в первом случае есть
единственный эффект, во втором библиотека не меняется, а trace объясняет оба
исхода.

### Самоконтроль

**Почему rejection передаётся модели как tool result?**

Модель ранее создала assistant tool call и ожидает связанный ответ tool. Такой
результат сохраняет причинную связь и позволяет явно сообщить, что операция не
выполнена, не маскируя решение под системную ошибку.

**Почему обычное сообщение «нет» недостаточно?**

В чате может быть несколько обсуждаемых действий, повторная доставка и
неоднозначный язык. Специальный endpoint авторизует пользователя и адресует
конкретный pending ID, поэтому решение невозможно случайно применить не туда.

**Что делать, если после reject не осталось бюджета шагов?**

Сначала надёжно сохранить reject и отсутствие эффекта, затем завершить run
контролируемым статусом. Нельзя ради красивого финального текста сбрасывать
лимит и запускать неограниченное продолжение.

### Совет на будущее

Причину отказа можно добавить позже как необязательный пользовательский текст,
но её нельзя интерпретировать как новые исполняемые инструкции без нового
цикла планирования и approval.

## 6.7. Конкуренция, срок действия и границы доступа

### Результат итерации

Устаревшее, чужое, просроченное или параллельно подтверждаемое действие не может
изменить данные. Защитные инварианты проверены негативными и конкурентными
тестами.

### Что реализуем

- Применим conditional update по status/version либо блокировку строки внутри
  транзакции для захвата pending action одним запросом.
- Отклоним решение, если:
  - `user_id` не совпадает;
  - action не `pending`;
  - `expires_at` наступил;
  - run уже завершён или имеет другую версию;
  - tool больше не зарегистрирован как ожидаемая destructive-операция.
- При первом обращении к просроченному действию зафиксируем `expired` без
  побочного эффекта.
- Добавим тест двух почти одновременных approve из независимых sessions.
- Проверим повтор после сетевого timeout и повтор после рестарта приложения.

### Зачем это нужно

Последовательные happy-path тесты не обнаруживают двойной клик, два browser tab,
повтор HTTP-клиента или решение старой карточки. Именно такие гонки превращают
правильный в одиночном запуске код в повторный destructive effect.

### На что обратить внимание

- Проверка `if pending` в Python до commit не является блокировкой: две
  транзакции могут одновременно увидеть одно состояние.
- Ошибки доступа не должны раскрывать, существует ли чужой pending action.
- В тестах нужны независимые DB sessions; два вызова через одну session не
  моделируют конкуренцию.
- Время берём через внедряемые часы или контролируемый источник, чтобы expiry
  тестировался без `sleep`.
- SQLite имеет ограничения конкурентности; тест обязан проверять инвариант, а
  не притворяться полной моделью PostgreSQL.

### Проверка

- Негативный: approve чужого action не меняет данные.
- Негативный: expired action не вызывает handler.
- Негативный: stale run version отклоняется.
- Concurrency: из двух approve только один получает право на исполнение.
- Restart/retry: повтор после новой app/session не повторяет effect.
- Security: ответы для отсутствующего и чужого action не раскрывают детали.

### Критерий готовности

Во всех тестах — последовательных, повторных и конкурентных — destructive
handler вызывается не более одного раза, а неавторизованный пользователь не
получает ни эффект, ни сведения о действии.

### Самоконтроль

**Чем optimistic locking отличается от обычной проверки статуса в Python?**

Optimistic locking включает ожидаемую версию в атомарный `UPDATE` и проверяет
число изменённых строк. Обычная проверка отделена от записи: между `SELECT` и
`UPDATE` другая транзакция может изменить состояние.

**Что означает expiry: автоматическую отмену действия или только запрет
исполнения?**

Критичный инвариант — после срока handler не запускается. Перевод в `expired`
можно делать лениво при обращении; фоновая задача нужна только если продукт
требует мгновенно обновлять интерфейс без запроса.

**Можно ли обещать exactly-once при вызове внешнего сервиса?**

Не без сотрудничества внешней стороны или дополнительного протокола. Локальная
транзакция не откатывает уже принятый внешний запрос. Корректная формулировка —
at-most-once попытка либо effectively-once при поддержке idempotency key.

### Совет на будущее

Перед переходом на PostgreSQL повторить конкурентный тест на целевой СУБД и
явно выбрать между conditional update и `SELECT ... FOR UPDATE`. Не переносить
предположения SQLite о блокировках в production.

## 6.8. Сквозной acceptance-сценарий и закрытие этапа

### Результат итерации

Полный backend workflow демонстрирует оба исхода решения, восстановление после
рестарта и защиту от повтора. Документация и trace позволяют объяснить каждый
переход без чтения внутреннего кода agent loop.

### Что реализуем

- Добавим acceptance-сценарий approve:
  request → tool proposal → waiting → restart/session change → approve →
  единственное удаление → completed.
- Добавим acceptance-сценарий reject:
  request → waiting → reject → отсутствие удаления → completed.
- Проверим API-контракты статусов и approval DTO.
- Проверим trace: предложение, ожидание, решение, исполнение/отказ и финал имеют
  отдельные типы или однозначные поля.
- Выполним все unit, integration и acceptance тесты без реальной сети.
- Проверим Alembic upgrade с предыдущей ревизии и `alembic check`.
- Обновим README, основной roadmap и прогресс этого документа.
- Проведём ручной smoke через HTTP на локальной базе.

### Зачем это нужно

Компоненты могут быть зелёными по отдельности, но потерять `tool_call_id`, run
version или историю на границе HTTP и новой session. Acceptance-тест проверяет
процесс как долговечную последовательность состояний, а не один вызов функции.

### На что обратить внимание

- Fake provider доказывает orchestration backend, но не качество формулировки
  реальной модели. Assertions строятся по status, tool result и данным БД.
- Тест не должен считать финальный русский текст машинным контрактом.
- Перезапуск моделируется созданием нового app/session, а не повторным чтением
  из identity map той же session.
- `remove_book` остаётся доступен модели только потому, что его регистрация
  теперь всегда проходит через approval policy.
- Документация должна честно различать локальную атомарность и гарантии для
  будущих внешних эффектов.

### Проверка

- Полный test suite проходит.
- `alembic upgrade head` работает на чистой и обновляемой базе.
- `alembic check` не находит незаписанных изменений схемы.
- Approve acceptance фиксирует ровно один эффект даже после повтора.
- Reject acceptance фиксирует ноль эффектов.
- Ручной smoke показывает понятный pending summary и оба endpoint.

### Критерий готовности

Все критерии этапа 6 из основного roadmap доказаны автоматическими тестами:
pending переживает рестарт, до approval нет изменения, повтор безопасен, а trace
разделяет предложение, решение и исполнение.

### Самоконтроль

**Что доказывает acceptance-тест с fake provider, а чего не доказывает?**

Он доказывает детерминированную оркестрацию: сохранение, паузу, HTTP-решение,
возобновление и эффект. Он не доказывает, что произвольная реальная модель всегда
выберет правильный tool или сформулирует хороший финальный текст.

**Почему процесс нужно проверять после создания новой app/session?**

Human-in-the-loop разделён человеческой задержкой и почти неизбежно пересекает
границы запросов и процессов. Тест в одной session может случайно проходить за
счёт кэша ORM и не обнаружить несохранённые данные.

**Когда destructive tool можно безопасно оставить в production registry?**

Когда любой путь из agent loop сначала применяет закрытую backend policy,
сохраняет validated action и останавливается до авторизованного решения, а
прямое доверенное исполнение недоступно через пользовательский API.

### Совет на будущее

На этапе frontend карточка approval должна отображать только backend summary и
идентификатор pending action. UI не должен заново вычислять объект действия или
передавать его arguments при подтверждении.

## Финальный checkpoint этапа 6

Перед переходом к React нужно уметь показать на тестах и через HTTP:

- destructive proposal не меняет библиотеку;
- pending action восстанавливается после перезапуска;
- approve исполняет сохранённые arguments ровно один раз;
- reject не вызывает handler и позволяет run завершиться;
- чужое, просроченное и устаревшее решение безопасно отклоняется;
- два параллельных approve не создают два эффекта;
- trace объясняет, что предложила модель, что решил пользователь и что исполнил
  backend;
- все сценарии этапов 1–5 остаются зелёными.
