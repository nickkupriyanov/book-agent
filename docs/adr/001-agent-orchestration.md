# ADR-001: оставить собственный линейный agent loop

- Статус: принято
- Дата: 2026-09-14
- Контекст: архитектурная ревизия после этапа 10

## Решение

Book Agent пока сохраняет собственный `AgentService`. Переход на Agents SDK или
graph workflow сейчас не решает наблюдаемую проблему проекта и добавил бы второй
набор понятий поверх уже работающих state, trace, tools и approval.

## Почему текущее решение достаточно

Текущий workflow линейный и ограниченный:

1. модель возвращает финальный текст или один/несколько tool calls;
2. registry валидирует и выполняет разрешённые вызовы;
3. destructive вызов создаёт одну durable pause;
4. после approve/reject тот же run продолжается;
5. step budget и повтор одинаковых вызовов останавливают цикл.

Этот код небольшой, покрыт детерминированными evals и хранит состояние в явных
таблицах. Поэтому его поведение проще изучить напрямую, чем через framework.

## Рассмотренные варианты

### Custom loop — выбран

Плюсы: видны все переходы состояния, минимальная зависимость, policy и
идемпотентность принадлежат приложению. Минусы: streaming, handoffs,
параллельные tools и сложные checkpoint-механизмы пришлось бы создавать самим.

### Agents SDK — пока не выбран

Имеет смысл, когда проекту действительно понадобятся стандартные handoffs,
streaming событий, tracing-интеграции или широкий набор совместимых tools.
Сегодня ни одного такого требования в MVP нет.

### Graph workflow — пока не выбран

Имеет смысл для нескольких ветвящихся процессов, параллельных узлов, нескольких
типов human-in-the-loop pause и возобновления с разных checkpoints. Текущий
процесс имеет одну линию и одну форму pause, поэтому граф скроет простую логику.

## Измеримые триггеры пересмотра

Решение открывается заново, если выполняется хотя бы одно условие:

- появляются два независимых agent handoff или больше;
- появляются два типа durable pause или ветвление, которое нельзя ясно выразить
  одним `AgentRunStatus` и последовательностью steps;
- нужен параллельный запуск tools, а его задержка измеримо мешает продукту;
- streaming и стандартная трассировка требуют больше собственного glue-кода,
  чем сам agent loop;
- изменение workflow регулярно затрагивает policy, persistence и API одновременно
  и приводит к дефектам, которые graph/checkpoint abstraction предотвращает.

## Последствия

Мы продолжаем улучшать существующий loop только под подтверждённые требования.
Любая миграция должна повторно прогнать тот же versioned dataset и сохранить
security contract. Framework выбирается по устранённой проблеме и метрикам, а не
по популярности.
