# Этап 11: микро-роадмап

Финальный этап проверяет, соответствует ли фактическая система её документации,
и фиксирует следующий архитектурный выбор. Каждая итерация завершается
отдельным коммитом.

Вернуться к общей карте: [ROADMAP.md](./ROADMAP.md).

## Граница этапа

Целевой результат:

1. реальные зависимости слоёв описаны и проверяются тестами;
2. security-инварианты собраны в одном исполняемом контракте;
3. устаревший прямой LLM-путь удалён;
4. одна команда выполняет HTTP demo: read, multi-step write и approval;
5. eval baseline закреплён стабильным артефактом;
6. threat model и известные ограничения честно отделяют учебную готовность от
   production readiness;
7. ADR объясняет, почему custom loop остаётся и при каких измеримых условиях
   решение нужно пересмотреть.

Не добавляем новый агентный фреймворк, streaming, очереди, multi-agent или
production infrastructure: этап должен уменьшать неопределённость и сложность,
а не начинать новый продуктовый цикл.

## 11.1. Архитектурная карта и dependency contracts

### Результат

Документация показывает фактические слои, направления зависимостей и границы
данных; тесты ловят нежелательные импорты инфраструктуры в домен и harness.

### Проверка

- Домен не импортирует FastAPI или SDK модели.
- Agent loop зависит от `LLMProvider` и ToolRegistry, но не от DeepSeek.
- Tools не выполняют SQL напрямую.
- Карта содержит write flow от HTTP до БД и обратно.

## 11.2. Исполняемый security contract

### Результат

Одна группа тестов подтверждает allowlist, strict validation, approval,
idempotency и user scope без побочных эффектов при атаке.

### Проверка

- `execute_sql` остаётся unknown tool.
- `user_id` отсутствует в аргументах user-scoped tools.
- Destructive tool нельзя выполнить через agent loop без approval.
- Чужие заметки и библиотека недоступны.

## 11.3. Удаление устаревшего прямого chat path

### Результат

В приложении остаётся один пользовательский LLM workflow через AgentService;
вызов модели больше не обходит trace, tools и policy через `/api/chat`.

### Проверка

- `/api/chat` отсутствует.
- Контракт `LLMProvider` и fake остаются доступны agent loop и evals.
- Полный suite и frontend не зависят от удалённого пути.

## 11.4. Воспроизводимый HTTP E2E demo

### Результат

Одна команда на временной SQLite выполняет read, поиск с добавлением и
destructive approval, после чего печатает компактный JSON-результат.

### Проверка

- Demo не использует сеть, постоянную БД или API key.
- Write меняет БД ровно один раз.
- До approval книга существует, после approval удалена.
- Каждый run содержит safe trace.

## 11.5. Baseline и architecture decision record

### Результат

Стабильный baseline фиксирует dataset/prompt и ключевые метрики; ADR выбирает
custom loop и называет конкретные триггеры перехода на SDK или graph workflow.

### Проверка

- Baseline соответствует текущему обязательному eval run.
- Изменённый dataset или метрика обнаруживаются.
- ADR сравнивает custom loop, Agents SDK и graph workflow по требованиям проекта.

## 11.6. Threat model, ограничения и закрытие проекта

### Результат

README описывает фактические команды и структуру, threat model перечисляет
активы, границы доверия, существующие controls и остаточные риски.

### Проверка

- Чистые миграции проходят на SQLite и PostgreSQL.
- Backend, evals, demo, frontend tests/build/lint проходят.
- Все четыре MVP-сценария покрыты автоматическими проверками.
- Документация не называет учебный проект production-ready.
